# S-pack — 虚を詰める (Void Packing, T9)

## Question

RESEARCH.md v5 Y7 第二補正（作者が普段の作り方を自ら言語化した箇所）:

> 「ボリュームの中にランダムな形態をパッキングする」「ある形態を実体としたときに、内部に
> できるだけ虚の物体を詰め込んでブーリアン除算したときに残る、元の形態の骨組みのようなものを
> 作りたい」

積む単位は虚。作品は残り物。この Study の問い:

- 実体（ホスト）の内部へ虚の球を貪欲にパッキングし、host − void を滑らかに合成すると、
  **殻に穴が空き → 膜と柱が生まれ → 骨組みだけが残る**、という遷移が、
  遷移用のつまみを直接引かなくても**パッキングの帰結として**現れるか
- 詰め方の「偶然」（乱数の配置順）が、骨の太さのムラ・偶発的な開口・膜と柱の混在を
  生むか（Voronoi 分割のような均質で死んだ分割との違い）
- 隙間 g（骨の最小太さ）という一つのつまみが、印刷可能性の計器として正直に機能するか

## Setup

`src/studies/pack/` に自己完結。`pack.html` から起動。

- **実体（ホスト）**: S1 と全く同じ場の定義。`cloud-sculpt/field.ts` の `Ball`・`FieldParams`・
  `fieldSdf`・`smoothMin`・`growBalls` をそのまま import（コピーしない）。既定は S1 と同じ
  `DEFAULT_FIELD_PARAMS` での grow。「S1 レシピを読み込む」ボタンで過去作を host として輸入できる
  （`history.ts` の `loadHostFromS1Recipe` — S1 自身の `parseRecipe`/`replay` を使って再生し、
  結果の球リストを `loadHostFromS1Recipe` という1エントリとして記録する。foam の `loadBalls` と
  同じ設計）
- **虚**: もう一つの `Ball[]`（`field.ts` の独自 id カウンタ `freshVoidId`）。当面は球のみ
  （T9「やらないこと」どおり、歪んだ塊は次便）
- **合成 SDF**（`field.ts` の `compositeSdf`）:
  `composite = opSmoothSubtraction(voidField, hostField, roundK)`
  where `opSmoothSubtraction(d1, d2, k) = smooth(max(-d1, d2))`（Inigo Quilez の
  smooth subtraction、https://iquilezles.org/articles/distfunctions/ ）。
  `d1 = voidField`・`d2 = hostField` と渡すことで `smooth(max(hostField, -voidField))` —
  T9 §1 の式そのものになる。`k <= 0` は硬い論理減算に退化する（`field.ts` の `smoothMin` と
  同じ設計方針）
  - **仮決め（丸さ k は一本）**: 指示書は「丸さの k」を単数で呼んでいる。虚どうしの smooth union
    と、host − void の減算そのものの丸めに、同じ `roundK` を再利用した（未発注の2本目のつまみを
    増やさない判断）。虚が密集した場所は虚どうしが融合して一つの空洞になり、疎な場所は個別の
    穴のまま残る — これも「詰め方の偶然」の表れとして残した
  - レイマーチのシェーダ (`shaders.ts`) は host 用と void 用、二つの球配列を持ち、CPU
    (`field.ts`) と全く同じ式で合成する。標準的なスフィアトレーシングは、食い込みで開口が
    生まれたときも特別な処理なしに動く: 光線が外殻を透過すると、composite sdf が正（空洞内）
    のまま進み続け、空洞の奥の壁（composite sdf が再び負）に当たるまで止まらない。
    「食い込みを上げると開口が見える」が自然にコードなしで出る
- **詰める手** (`field.ts` の `packVoidsGreedy`): T9 §2 の式をそのまま実装。
  ホストの bounding box（`cloud-sculpt/meshExport.ts` の `computeSamplingBounds` を再利用）から
  一様乱数で点をサンプルし、ホスト外なら棄却。ホスト内なら、その点に置ける最大半径:

  ```
  maxR = min(
    虚の大きさ上限,
    -hostSdf(p) - 隙間g + 食い込み,   // 表面制約。gap を引くことで
                                        // penetration=0 のとき必ず gap 分の殻が残る
    min over existing voids ( dist(p, void.center) - void.r - 隙間g )
  )
  ```

  `maxR < 虚の大きさ下限` なら棄却。採用する半径は **その点で許される最大値**
  （真の貪欲 — 「一様でよい」とされた分布は点のサンプリングの方に適用し、半径は
  幾何が許す最大を取ることで、疎な場所には大きい虚・密な場所には小さい虚という
  「大小混ぜる」が二重の乱数なしに自然に出る。理由は下記「仮決め」参照）。
  連続して`FAIL_LIMIT`回棄却が続いたら「置けなくなった」と判定して早期終了する
  （`FAIL_LIMIT = max(120, attempts×0.3)`、未校正のヒューリスティック）
  - **重要な修正（実装中に発見）**: 当初、表面制約を `-hostSdf(p) + penetration`
    （gap を引かない式）で実装したところ、`penetration=0` でも表面ぎりぎりに接する虚が
    生成され、`roundK`（丸め半径）がその接点を丸めて視覚的に小さな穴として見えてしまう
    現象を確認した（SDF 上は非開口〈dHost はゼロを跨がない〉が、`roundK` が gap を超えると
    薄い殻が視覚的に「開いて見える」）。表面制約にも gap を効かせる修正で、
    penetration=0 のときは常に gap 厚の殻が保証されるようにした（下記 Observation 参照）
- **履歴** (`history.ts`, studyId `"pack"`): `growHost` / `setHostParam` /
  `loadHostFromS1Recipe` / `setPackParam` / `packVoids` / `addVoid` / `removeVoid` /
  `clearVoids` / `clearAll`。**`packVoids` は結果の虚球リスト全体を引数に持つ**
  （T9 §2 の指示どおり — mpm の `freeze`/`seedMesh` と同じ設計: replay は乱数の
  ウォークを再実行せず、記録された結果をそのまま再適用するので、正本の再現は
  パッキングアルゴリズムが将来変わっても壊れない）
- **手動の虚の追加・削除**: 「虚を手で追加」ボタンでモードを切り替え、その状態で
  ホストの表面をクリックすると、その場所（法線方向に半径の半分だけ押し込んだ位置）に
  手動の虚を置く（`addVoid`）。既存の虚をクリックで選択、Delete キーまたはボタンで削除
  （`removeVoid`）。
  - **仕様の簡略化（仮決め）**: 手動追加のクリックは常に**ホストのみ**の SDF（`picking.ts`
    の `raymarchHost`、虚を無視）に対してレイマーチする。理由: 合成場に対してレイマーチすると
    既に開いた空洞の奥をクリックしたくなる場面が出るが、視線が空洞を透過する挙動の実装・検証の
    複雑さに対して、この Study の主眼（パッキングの帰結としての骨組みの創発）への寄与が薄いと
    判断し、範囲を「ホストの外殻をクリックして押し込む」だけに絞った
  - **ドラッグは実装していない（意図的な範囲決定）**: S-rings は差分ドラッグの再平面化バグ
    （rings/README.md の「作者実機で発見」の節）を踏んだ。同じ罠を踏まないための最も確実な方法は
    「そもそもドラッグを実装しない」という選択だった。虚の移動はこの Study にはない
    （置く／消すのみ）— 罠を回避したのであって、修正して安全に実装したわけではないことを明記する
- **計器** (`field.ts` の `estimateThinnestWall`・`estimateFillRatio`):
  - 最薄の肉: 「厳密でなくてよい」との指示どおり、二つの安価な代理指標の最小値。
    ①各虚の中心1点でのホスト表面までの残り厚み（`-hostSdf(void.center) - void.r`）
    ②虚どうしのペアごとの中心間距離−半径和（骨の太さ）。**限界**: 実際の等値面の
    最薄点はこれより薄いことがありうる（中心点サンプルなので壁の中腹を見ていない）—
    「保守的な推定」であって保証ではない、と正直に書く
  - 充填率: ホスト体積をモンテカルロ推定（bounding box 内の一様サンプルのうち
    `hostSdf < 0` の割合 × box 体積）し、虚の体積合計（各虚を独立球として `4/3πr³`、
    重なりは重複計算— 隙間制約でほとんど重ならないが、厳密ではない）との比。
    「粗い推定」であることを明記
  - mm 換算は「3Dデータ」パネルの最長辺 mm 設定と連動（`computeSamplingBounds` の
    `longest` を使った近似スケール — 実際のメッシュ境界箱とは若干異なるが、
    ライブ表示としては十分な近似）
- **出口**: `cloud-sculpt/meshExport.ts` の `buildMeshFromField`・`computeSamplingBounds`・
  `encodeObj`・`encodeBinaryStl`・`meshSummary` をすべて再利用（コピーせず import）。
  `pack/meshExport.ts` の `buildPackMesh` が `compositeSdf` を差し込むだけ。sourceBounds は
  ホストのみから計算する（減算は常にホストの体積以下になるため、ホストの bounds で十分 —
  `opSmoothSubtraction` の定義上、合成は決してホストの外側に材料を生まない）
  - **S1 レシピとしては書き出せない（T9 §4 の明示的な指示）**: S1 の正本は実の球だけで、
    虚を表現できない。この Study は**正本の語彙を初めて実+虚に拡張する**ため、
    レシピ形式は独自（`studyId: "pack"`）。S1 → pack の輸入（読み込み専用）はできるが、
    逆方向は意味を持たない
- **技術選定**: vite + three.js + 素の TypeScript。既存 Study と同水準の軽さ

### バグ修正の記録（実装中に発見・修正）

- 当初 `packVoidsGreedy` の表面制約が `-hostSdf(p) + penetration` のみで `gap` を引いて
  いなかったため、`penetration=0` でも虚がホスト表面に**接する**（残り厚み0）ことがあり、
  `roundK`（当時デフォルト0.15）がその接点を丸めて視覚的な小さい穴に見せてしまった
  （SDF 上は非開口だが、`roundK` > 実際の残り厚みだと肉眼には開口に見える、という
  smooth boolean 特有の現象）。修正: 表面制約に `- gap` を追加し、`penetration=0` では
  必ず `gap` 厚の殻が残るようにした。あわせて既定値を `gap=0.05`・`roundK=0.04`
  （`roundK <= gap` の関係）に調整し、初期状態が視覚的にも完全な閉殻になることを確認した
- **教訓（Hypothesis へ）**: 隙間 g は「虚どうし・虚と表面の間に残す最小の肉」という指示書の
  定義どおり実装すれば、視覚的な閉殻/開口の切り替わりも自然に正しくなる。roundK（丸さ）は
  独立した見た目のパラメータではなく、gap で保証された肉厚を「どれだけ滑らかに描くか」の
  ローパスフィルタのようなものであり、`roundK` が `gap` を上回ると、正しい閉殻でも視覚的には
  薄く／開いて見えることがある — これは実装バグではなく smooth subtraction の性質そのものだが、
  デフォルト値の選び方には直結する

### 水密の実測（完了条件4）

- 状態①（48虚、閉じた殻）: 解像度64/96/128 すべて **水密 OK**
  （openEdges=0, nonManifoldEdges=0; 三角形数 112,632 / 255,168 / 454,308）
- 状態②相当（565虚、多数開口、充填率60%）: 解像度64（2.08秒, 186,924三角形）・
  96（6.87秒, 449,956三角形）・128（15.38秒, 822,068三角形）すべて **水密 OK**
- 状態③（521虚、gap=0.008 の極薄骨、充填率67.5%）: 解像度64（173,156三角形）・
  128（763,920三角形）とも **水密 OK**
- **骨が細いときの水密の解像度依存**: 今回テストした範囲（gap 0.008〜0.05、虚数
  48〜565）では、foam Study（README にある「解像度を上げても水密性が単調に改善しない」
  という報告）のような NG は一度も再現しなかった。理由の仮説: `compositeSdf` は
  `fieldSdf`（真の smooth-min union、Euclid 距離場に忠実）どうしを Quilez の
  smooth subtraction で合成しているため、foam の `cellWall`/`cellEdge`（各点で独立に
  最近傍3球を取る非距離場的な代理指標）と違い、大域的に一貫した滑らかな符号場になっている
  可能性が高い。ただし**これは「壊れない」という保証ではない** — さらに極端な設定
  （gap をさらに下げる・虚を密集させすぎる等）や、より低い解像度（32以下）は
  この便では検査していない。正直に「今回テストした範囲では壊れなかった」とだけ書く
- メッシュ検査の所要時間は虚の数にほぼ比例して増える（合成 SDF の評価コストが
  host+void の球数の和に比例するため）。565虚・解像度128で約15秒（isolated Chrome
  software WebGL 環境の実測。デスクトップ実機では別途再計測が必要）

### 1. 地と図の反転（`field.ts` の `PackMode`）

- **`"carve"`（実体に虚を詰める、現行・既定）**: `composite = opSmoothSubtraction(voidField, hostField, roundK)`。T9 のまま無変更
- **`"fill"`（虚に実を詰める、新設）**: ホストは**型枠** — `packVoidsGreedy` は完全に無変更
  （ホストの内部にしか虚は置けない、という配置拘束にだけ使う）だが、`compositeSdf` は
  ホストを一切参照せず、詰めた球たちの smooth-union `fieldSdf(voids, roundK, ...)`
  を返す。**式（README に明示すべき箇所）**:
  `carve: d = opSmoothSubtraction(fieldSdf(voids,roundK), fieldSdf(host,hostK), roundK)`
  `fill:  d = fieldSdf(voids, roundK)`（host 完全無視、voids が空なら 1e5 = 「なにもない」）
  - モードは履歴の一操作 `setMode`（skin の `setMode` と同じ設計 — パッキング自体には
    触れないが、export→import の完全再現のために記録する）
  - **ワンタッチ往復**: 同じ `voids` 配列に対して `setMode` を呼ぶだけなので、パッキングの
    再実行は一切発生しない（skin の `プレートが実`⇄`形態が実` と同じ設計）
- **表示**: raymarch シェーダの `map()` も CPU の `compositeSdf` と全く同じ式で分岐
  （`uMode` uniform、0=carve/1=fill）。fill モードの raymarch は host を一切描かない
  （host は「型枠、印刷されない」ので raymarch でも登場させない、という仮決め — 半透明の
    下敷き表示は**ビーズ表示限定**の機能とし、raymarch には持ち込まなかった。理由:
    raymarch は単一パスの不透明合成で、smooth-min された固体とは別にもう一段の半透明合成
    レイヤーを重ねる実装コストが、この便の主眼〈反転の往復・改善の移植〉に対して重いと判断した）
- **STL 書き出し（水密・連結成分数、T13 完了条件1）**: `meshExport.ts` の
  `buildPackMesh(mode, ...)` がモードで分岐。fill モードのサンプリング境界は
  `computeVoidsBounds`（voids の中心±半径から直接計算 — host の bounds では
  penetration>0 で表面をはみ出した虚や手動追加の虚を裁ち落としてしまうため、skin の
  ring3d 由来の bounds パディングと同じ理由で voids 自身の実データから計算した）
  - **連結成分数** (`countConnectedComponents`、skin/meshExport.ts の同名関数の
    自己完結コピー — Study 間で import せず同じ式を独立に書く、pack/skin 間の既存の
    設計方針を踏襲): 反転モードで**分離部品がありうる**ことを正直に表示する
    （完了条件1の「連結成分数を正直に表示」）

### 2. 詰めの挙動を skin と揃える

- **乱数の続き**（`field.ts` の `packVoidsGreedy`）: skin が発見・修正したのと**全く同じ
  バグ**が pack にも眠っていた —— `hashSeed(params.seed)` は毎回同一の乱数列を再生する
  ため、2回目の「詰める」は1回目が消費した候補点をそっくりそのまま再試行して弾かれ、
  ほぼ +0 個になっていた。修正: `hashSeed(\`${params.seed}#${voids.length}\`)`
  （skin と全く同じ式、既存の虚の個数をシードに畳み込む）。`packVoids` は結果の虚リスト
  全体を引数に持つ既存の設計（T9）のため、この修正は replay の再現性に一切影響しない

- **飽和の処方箋**（`ui.ts` の `setPackResult`）: `result.stoppedEarly || result.placed === 0`

  「隙間 g」を小さくしてください。試行数を増やしても飽和は破れません」と表示する
  （skin の文言に倣った — 「試行数では破れない、破れるのはサイズと隙間」という構造は

### carve モードの連結成分数についての正直な発見（実装中に判明、想定外だった挙動）

penetration=0（閉じた殻、開口なし、`hasOpening: false`）の状態で63個の虚を詰めて
STL 検査したところ、**連結成分数が1ではなく解像度依存で 38 / 59 / 64（解像度64/96/128）**
という結果になった。当初は「閉じているはずなのに何故分離するのか」とバグを疑ったが、
検証の結果これは**バグではなく、marching tetrahedra が生成する境界面の位相として
正しい**ことを突き止めた:

- 内部に密閉された空洞（虚）を持つ立体の境界面は、**外殻1枚 + 密閉された空洞ごとに
  独立した内壁1枚**という、複数の閉じた2次元多様体の集合になる（中空の球が「外の球面
  ＋内の球面」という2つの独立した閉曲面であるのと同じ、ごく基本的な位相の事実）
- 検証: 虚0個（host のみ）で連結成分数=1（トリビアルに正しい）。63個の虚（全て
  penetration=0 で密閉）で解像度128のとき連結成分数=**64**（= 63虚 + 外殻1 と正確に一致）。
  解像度を下げると（64→38、96→59）、隣接する虚どうしの内壁が低解像度のグリッドで
  部分的に融合してしまい、理論値64より少なく出る（roundK による滑らかな融合が、粗い
  グリッドでは「別々の虚のはずが同じ内壁として量子化される」ことがある、という
  解像度依存の別の正直な限界）
- **penetration>0 で外殻に到達した虚は、その虚の内壁が外殻と融合して1つの連結成分に
  溶け込む**ことを確認した（penetration=0.3・74虚・解像度96で連結成分数27 — 63個
  密閉時の想定64近辺よりずっと少なく、多くの虚が実際に外殻へ到達して融合したことを
  裏付けている）
- **完了条件1が求める「連結成分数を正直に表示」の意味は、carve モードと fill モードで

  中身がくり抜かれているだけ）」の混在でありうる — carve モードで連結成分数が

作者発注: 「球体じゃなくて**雲自体を入れ込む**ことは可能だろうか」（2026-07-14）。

### Setup v0.3

- **単位（`field.ts` の `PackUnit`）**: 詰めるものが球1個から「単位」に昇格。
  単位 = 球の群 `balls[]` ＋ 単位内ローカルな丸さ `localK` ＋ 外接球
  （`center`・`outerRadius`）。skin の `Patch`（点群を持つ単位）と同じ所有構造
  （球は単位への逆参照を持たない。単位の `balls` 配列そのものが所有記録）
- **単位の切替（球 / 雲）**: `PackParams.unitKind`
  - `"sphere"`: 球1個。**localK は数式に一切現れない**（1球はブレンド相手がいない）ため、
    球モードは v0.2 と数値レベルで同一 — 検証で初回/2回目/3回目の詰めが
    63/+44/+18 と T13 の実測記録に**1個単位まで一致**することを確認した（無退行は
    テストではなく構成で保証されている）
  - `"cloud"`: 球の小群（既定3〜7個、つまみで1〜10）。growBalls と同じ流儀
    （等方ランダム方向＋中心バイアス `pow(rng, 0.6)`）で、**詰めの貪欲ウォーク自身の
    rng から生成**するため単位ごとに形が違い、かつ同じシードなら同じ結果
    （決定性は id を除く JSON 比較で実測確認）。**単位生成の式**:
    ```
    count  = round(unitBallsMin + rng·(unitBallsMax − unitBallsMin))
    offset = pow(rng, 0.6) · outerRadius · 0.62        // 中心バイアス
    方向    = 等方ランダム（theta, phi）
    baseR  = (outerRadius − offset) · (0.55 + 0.35·rng)
    r      = min( max(outerRadius·0.1, baseR·(1 − spread/2 + rng·spread)),
                  outerRadius − offset )               // ←外接契約のクランプ（下記バグ記録）
    ```
- **大きさ下限/上限 = 単位の外接半径**: 既存の minR/maxR のつまみはそのまま、意味が
  「その点に置ける単位の外接半径」に再解釈された（球単位では従来どおり球の半径そのもの）
- **clearance は外接球で粗く（近似の明記）**: 単位どうしの衝突判定は
  `dist(候補点, 単位.center) − 単位.outerRadius − gap` のみ。**雲の実球どうしの精密判定は
  しない** — 指示書の指定どおり（「詰め方の偶然が価値」）。帰結として、雲単位の実球は
  外接球より内側にあるため、実際の肉は計器の値より**厚い**方向にずれる（安全側）
- **二段の smooth-min**: `unitSdf`（単位内、localK）を `unitsFieldSdf`（単位間、roundK）が
  包む入れ子。CPU（field/picking/meshExport）と GLSL（shaders.ts の
  `uUnitStart/uUnitCount/uUnitLocalK`、`VOID_MAX_UNITS`=64）が同式。roundK の意味
  （単位間の融合＋carve の減算丸め）は v0.2 から不変
- **S1 レシピを単位にする（`loadCloudPrototype` op）**: S1 の replay で球リスト＋k を得て
  原型として登録（`loadHostFromS1Recipe` と同じ「他 Study の replay を借りる」設計）。
  配置時は **正規化スケール**（scale = 置ける外接半径 / 原型の包含球半径。包含球 =
  重心 + max(dist+r) の保守的近似 — 真の最小包含球ではない、と明記）＋
  **ランダム回転**（Rodrigues、単位ごと）で複製。原型は複数登録でき、単位ごとに
  ランダム選択。原型の k もスケール連動（localK = 原型k × scale）。
  原型を読み込むと unitKind が自動で「雲」に切り替わる（通常の setPackParam として記録）
- **手続き雲へのランダム回転は適用していても統計的に無意味**（等方生成を回しても等方のまま）
  だが、原型複製では唯一の単位間差異源。一本のコードパスに統一した（仮決め）
- **履歴**: `packVoids`/`addVoid`/`removeVoid` → `packUnits`/`addUnit`/`removeUnit` に改名。
  すべて**結果の単位データ（単位境界含む）を引数に持つ**現行の流儀を維持 — replay は
  いかなる rng も再実行しない。手動追加も生成結果の PackUnit を丸ごと記録
- **計器の変更（正直さの向き）**: 最薄の肉は**単位の外接球ベース**に変更 — これは
  パッカー自身が enforce した同じ粗い指標であり、実球で測ると「アルゴリズムが保証して
  いない細かさ」を表示してしまう（逆向きの不正直）。球単位では v0.2 と数値同一。
  充填率は逆に**実球ベースのまま**（外接球では雲の中身スカスカ分を過大計上する）。
  UI の計器欄に近似の注記を常設
- **ビーズ表示**: 全単位の全球を描く（単位あたり3〜10球で点数が跳ね上がる、指示書の
  指摘どおり）。選択ハイライトは**単位の全球**に効く。レイマーチ容量は
  球数(192)と単位数(64)の**二本立て**になり、どちらかの超過で自動切替が発火 —
  雲単位では球予算が3〜10倍速く尽きるため、自動切替が常用経路になる
  （1404球のビーズで 0.285 ms/frame〈CPU 提出コストの下限、T13 と同じ
  benchmarkRender の限界つき〉。しきい値自体は据え置きで妥当と判断した —
  超過判定が球数・単位数の両方を見るようになった今、しきい値は「レイマーチが
  正しく描ける上限」という本来の意味だけを持つ）

  連結成分数 > 1 は密閉された内部空洞の壁を数えているだけで、印刷される部品数とは
  限らない」ことが判明した（README「正直な発見」参照）が、`meshSummary` の
  「部品数 N」という文言は carve/fill で同じ言い回しのまま。carve モードでは
  「（うち内部空洞の壁を含む）」等の注記を添える、あるいは外殻とそれ以外を
  区別して数える、といった改善の余地がある
- **骨組みだけ状態の追い込みに、fill モードの視点も使う**: 反転して見ると
  「詰めた実の集積」が母体の形をどれだけ暗示するかが直接見えるため、T9 Next に
  残っている「外殻消失の追い込み」の観察をfill モードから行うと分かりやすいかもしれない
- fill モードの raymarch に host の半透明下敷きを重ねる（今便はビーズ表示限定の
  仮決めとして見送った — §Setup 参照）
- ビーズ表示の carve/fill 色分けを、色覚多様性に配慮した符号化（形状差・パターン等）に
  拡張する余地（今便は色相のみでの区別）
