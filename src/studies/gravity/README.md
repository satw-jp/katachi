# S2 — 重力を入れる (Gravity)

## Question

粗い力の素描（FEM でも梁でもない、ただの「質量の流れ ÷ 断面積」）でも、
こねたときの手応えの向き（細くすれば赤くなる、支えを失えば真っ赤になる）は合うか。

## Setup

- **場の定義**: S1（`src/studies/cloud-sculpt/`）の `Ball[]` と `FieldParams` をそのまま輸入する
  （`field.ts` / `picking.ts` を import、コピーしない）。雲の形の正本は S1 と同じ
- **地面**: y = 0 の無限平面。レイマーチのシェーダ内で `map(p) = min(mapCloud(p), mapPlane(p))`
  として雲の SDF とハード min で合成（雲と地面は smooth-min しない — 別の物質という前提）。
  接地判定・当たり判定（クリック追加/選択）は雲の SDF のみで行う（地面はクリックに反応しない）
- **接地させる**: 新しい履歴 op `snapToGround`（引数なし）。全球の最下点
  (`min(y - r)`) が 0 になるよう、現在の球の位置から決定的に計算した delta を y に加算する。
  引数を持たないのは「現在の場の関数」として replay 時も同じ delta が再現されるため
- **苦しさの近似**（`physics.ts`）:
  1. 球を節点、中心間距離 < r₁+r₂ の球対を辺とする無向グラフを作る
  2. 地面に触れている球（`y - r ≤ 0.02`）を地面への距離0の起点として、
     Dijkstra（辺の重み = 中心間距離）で「地面までの最短経路木」を作る
     （RESEARCH §3「解き方の5系」でいう②図で解く — 経路は最短、全経路等分配ではなく択一）
  3. 木を後順走査し、各球の「担いでいる体積」= 自分の体積 + 自分より上流（木の子孫）の体積の総和
  4. 各球の断面積 = 親球との重なりレンズの面積（地面直結の球は地面との接触円の面積）。
     二球が重なる円の断面積は標準の球殻交差公式、地面接触は `r² - y²` から円の半径を出す
  5. 苦しさ(生) = 担いでいる体積 ÷ 断面積。`STRAIN_REFERENCE = 6.0`
     （S1 既定値 count=12, radiusBase=0.7 の雲で試算し、赤〜青のグラデーションが
     画面内に収まるよう経験的に選んだ表示用の較正定数。材料定数ではない）で 0..1 に正規化し、
     `pow(t, 0.7)` で低〜中域が見やすいようガンマをかけてから青↔赤を補間
  6. 地面まで経路が無い球（Dijkstra が到達できない）は無条件で苦しさ最大（`island: true`）
- **色は導出物**: `computeStrain()` は毎フレーム `state.balls` から再計算する純粋関数。
  履歴には一切乗らない（記録されるのは `snapToGround` 等の操作のみ、T2-gravity.md §4）
- **色の値**（**作者承認済み 2026-07-09**「色自体はこれでいい」— 全 Study 共通スケールとして確定。
  以後変えない。変える場合は骨子を改訂して版を残す — AGENTS §5）:
  - 青（楽）= `rgb(0.30, 0.55, 0.95)`、赤（限界）= `rgb(0.95, 0.25, 0.20)`。
    アプリの既存パネル配色（`--accent` #6fb1ff 系、`--danger` #ff6b6b 系）を
    彩度を上げて連続スケール用に再設計。選択中の球のハイライト（黄）と重ならない色域を選んだ
  - 地面はグリッド柄の濃いグレーで、苦しさの色と混同しないよう明確に別の質感にした
- **常設の正直さ表示**: ビューポート左上に固定バナー
  「粗い近似: 質量の流れ ÷ 接続断面積。FEM ではない。実物の保証はしない。（S3 で実物と校正予定）」
  （パネルの外、スクロールでは隠れない `position: absolute` 要素）
- **手の履歴**: S1 と同じ `[{t, op, args}]` 形式に `snapToGround` を追加しただけ。
  `formatVersion/studyId/entries` の Recipe 形式も同じ。`studyId: "gravity"` で S1 のものと区別
- **技術選定**: S1 と同一（vite + three.js + 素の TypeScript）。理由も同じ（README 参照）。
  マルチページ vite ビルド（`index.html` / `gravity.html` を別エントリとして `vite.config.ts`
  の `build.rollupOptions.input` に登録）で、ビルド後もリンクで行き来できる形にした
- **入り口**: 互いのパネル上部に素朴なテキストリンク（S1→S2, S2→S1）。ハブ画面は作らない

  雲が地面グリッドの上に浮いた状態で表示され、球ごとに青〜赤のグラデーションが付いた
  （既定の雲は一部の球がすでに y<0 に埋まっており、`snapToGround` 前でも地面に触れている球があった）。
  「接地させる」を押すと `history` に `snapToGround` が1件積まれ、全球の y が一様に
  +1.35 ほど持ち上がり、最下点がちょうど y=0 になった（`window.__gravity.getBalls()` で確認）。
- 合成テスト（`importJson` で最小構成を直接注入）で以下を確認した:
  - 地面に接する球1個＋その上に重なる球1個の塔で、上の球の半径を 0.5→0.35 に細くすると
    正規化された苦しさが 0.396→0.630 に上昇（赤に流れる）。0.5→0.75 に太くすると
    0.396→0.426 とわずかに悪化した — **これは既知の限界**（Hypothesis 参照）
  - 完全に孤立させた球（他のどの球にも地面にも触れない）は常に `island: true, normalized: 1`
  - 地面に点接触（半径と同じ高さで正確に接する）する球は接触円の面積が理論上 0 になり、
    苦しさが発散して常に最大（1）になる。これは球体と平面の数学的な点接触の帰結であり、
    実際の雲（既定の12球）でも1球だけ突出して真っ赤になる箇所として現れた
  - `exportJson()` → `importJson()` の往復で `getBalls()` と `getStrain()` が完全一致
    （`JSON.stringify` 比較で同一）。色は場からの再計算のみで再現され、履歴には残っていない
- **見つかった限界（記録として残す）**: ある球が他の球の支持のハブになっている場合、
  その球を極端に細くして周囲との重なりが消えると、支えていた球たちが最短経路の別ルートで
  地面につながり直し、当のハブ球自身の「担う体積」が急に小さくなって、かえって苦しさが
  下がることがある（プレビューで実測: r=0.82→0.10 で正規化苦しさ 0.18→0.04）。
  緩やかに細くしている間（重なりが残っている間）は一貫して赤くなる方向で動くが、
  重なりが完全に切れる境界を跨ぐと不連続に振る舞いが変わる。これは
  「グラフの重なりで接続を決める」モデル自体の性質であり、バグというより
  近似の限界として記録する（S4「細くする」や後続の育て直しで再考の余地あり）

## Hypothesis

- 苦しさの「向き」は、同じ経路トポロジーのまま径を変える範囲（つまり重なりが保たれている間）
  では信頼できる。トポロジーが変わる境界（重なりが切れる／新しい経路が生まれる）をまたぐと
  向きが逆転しうる — これは実物の破壊試験（座屈・接合部の破断）でも起こる非連続性に近く、
  雲性の限界（RESEARCH §9「雲性はどこで死ぬか」）と地続きの問いかもしれない
- 球と地面の点接触が発散する挙動は、実際には接触が有限の面積を持つ（材料の弾性変形）ことの
  裏返し。次に育てるなら「最小接触半径」のような下駄を履かせて発散を丸めるか、
  あるいはこの発散自体を「そこが本当に危ない」というシグナルとしてそのまま活かすか、
  作者と相談したい
