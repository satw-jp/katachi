# 花を詰める — Flower Packing Spike

## Question

作者の要望（2026-08-09、原文）:

> katachiのSRFpackに例えば３や４の球体からなるお花をパックしてみたいと思った
>
> 上記の形状に限らずパッキングをできるようにしたい
>
> hikariが別で実装動いてるからどういうふうに進めたら良いか一緒に考えたい

形を保つ Rigid packing と、押されて変形する Soft packing の両方を見たいか確認したとき、作者は
次のように答えた（同日、原文）:

> 両方みたい

同じ Flower、同じ配置面、同じ Seed でも、単位が外部の拘束へ抵抗する場合と、応答して変わる場合で、
詰まり方・隙間・単位同士の関係はどう変わるか。単球の当たり判定と、花芯＋花弁を覚えた複数球の
当たり判定では、何が観察できるようになるか。

作者から実画面の目視後、次の問いが加わった（2026-08-09、原文）:

> 花について、いまは球体のままだけど
> 花になる形態自体は一体にできる？

できる。配置と衝突判定では花芯＋花弁の複数球を保ちながら、形態の表示・Freeze・mesh書出しでは
それらを一つの scalar field として smooth union し、連続した一体形として実体化できる。
「一体」は、見た目が滑らかにつながること、mesh が一つの watertight component になること、Softでも
花芯と花弁の接続が切れないことの三段階に分け、同じ言葉で混同しない。

## Setup

- Flower は一つの花芯球と四つの花弁球からなる。高精細な花ではなく、単位と Instance を分けるための
  最小モチーフである
- `硬さ` 比較は同じ初期配置を、左 Rigid / 右 Soft として解く。Rigid は花全体だけが移動し、Soft は
  花弁球が花芯との接続を保ちながら rest offset からずれる
- `当たり判定` 比較は両方 Rigid のまま、左 L0 外接球 / 右 L1 複数球として解く
- Domain は Plane と Sphere Surface。Sphere は位置から normal と接線二軸を作り、花を外向きに置く
- solver は seed 付き初期配置から、proxy 球の貫通を接平面方向へ押し戻す素朴な反復緩和。Soft は
  変位の一部を花弁の局所 offset へ渡し、各反復で rest shape へ弱く戻す
- Gap は solver 固有値ではなく、各 collision proxy 半径へ半分ずつ加える clearance inflation として扱う
- `比較を保存 JSON` は左右の解を保存・再読込する。`右側をFreeze` は component sphere を実体化した
  draft Snapshot を保存するが、まだ Hikari Snapshot v1 ではないことをファイル内に明記する
- `球をそのまま / 一体の花` はPacking結果を変えない表示切替。一体表示は花ごとに5球のSDFを
  smooth unionし、Softで花弁が離れても形態の接続が失われないよう花芯—花弁間の細いneck fieldを加え、
  Marching Cubesでその場の面を表示する。現段階のFreezeはまだcomponent sphereであり、このpreview meshを
  watertightな製造用meshとして保存する機能ではない
- Softは花弁ごとのrest位置からの移動量を花半径に比例した範囲へ制限し、接触解消後のpolishでも同じ制約を
  外さない。L1衝突Proxyは花芯・花弁だけでなく、短い付け根上の補助球とsmooth-union膨張分のguardを含む
- `flower-form-spike.html` はPackingを隠し、左3枚・右4枚の花を一個ずつ同じ条件で大きく見る。操作は
  花弁の開き・付け根の太さ・花芯の大きさ・元の球の重ね表示だけに限定する

## Observation

- **2026-08-09（実装観察）**: Flower を一つの rigid unit として保持する経路と、花弁の局所 offset を
  packing pressure へ応答させる経路を、同じ初期 Instance から分岐できた。これは「花」という見た目を
  Core に入れず、Motif の response の違いとして比較できる最小形になっている
- **2026-08-09（正直な計器）**: solver が反復上限へ達しても未解決なら `Packed` と呼ばず、collision数、
  最大penetration、Domain外、平均変形とともに「部分的に配置」と表示する
- **2026-08-09（Hikari境界）**: Freeze は光学値を一切持たず、形・生成条件・scale provenance・診断だけを
  保存する。Hikari Adapter が成立するまでは draft と明記し、現在の Hikari 実装を import しない
- **2026-08-09（初回の実画面）**: Sphere Surface、Seed 304、34 flowers、size 0.25、Gap 0.025で、
  RigidとSoftはいずれも未解決collision 0まで接触を解消した。Rigidの平均変形は0.0%、Softは10.1%。
  花芯を暗く、花弁を明るく分けたことで、Soft側でも「一個の花」が崩れずに局所関係だけ変わる状態を
  追えるようになった。これは見た目の優劣ではなく、変形が実際に観察できる最低条件の確認である
- **2026-08-09（Plane対照群）**: Planeへ切り替えると過密になりすぎないよう18 flowersへ落とし、seeded
  sunflower初期配置を使った。同条件でRigid/Softとも未解決collision 0、平均変形0.0%/1.1%となり、
  曲率の無い対照面でも同じ契約が働いた
- **2026-08-09（L0/L1目視）**: Proxy表示ではL0の外接球が花弁間の凹部を完全に覆う一方、L1は花芯と
  花弁それぞれの輪郭を残す。同じSeedで両方ともcollision 0へ収束し、配置の粗さの違いだけを比較できた。
  証拠: [Rigid / Soft](screenshots/rigid-soft-20260809.png)、
  [L0 / L1](screenshots/proxy-l0-l1-20260809.png)
- **2026-08-09（操作検証）**: 実座標のクリックでProxy表示と比較切替、実座標のドラッグで3D回転を確認。
  Sphere/Plane切替後も操作でき、ブラウザのwarning/errorは0件だった
- **2026-08-09（一体の花・目視）**: 初期表示を一体fieldへ変更し、同じ配置のまま球表示と往復できるように
  した。Rigidは花芯から4枚の花弁へ連続した十字状の面として読める。Softも平均10.1%の変形差を残しつつ
  接続が続く。実座標で表示切替と3D回転を確認し、Proxyを重ねると内部の5球と導出面の対応も見える。
  証拠: [一体のRigid / Soft](screenshots/unified-rigid-soft-20260809.png)、
  [一体面 + L1 Proxy](screenshots/unified-with-proxies-20260809.png)
- **2026-08-09（一体性の反証と補正）**: 最初のsmooth unionだけの実装は通常条件では接続して見えたが、
  高密度Soft fixtureで一部のcore—petal経路がfield外へ切れることを自動検査が発見した。見た目だけで
  「一体」と呼ばないためneck fieldを追加し、Rigid/Softの全花・全花弁についてcoreからpetalまで24分割
  した経路がfield内部に留まる検査を通した。これはwatertight mesh componentの検証とはまだ区別する
- **2026-08-09（作者のバグ発見）**: 作者が右のSoftを近接観察し、`みぎは一部バグっている` と指摘した。
  添付画像にあった平らな円盤状の面は、Softで花弁が移動しているのに、Marching Cubesのsampling cubeを
  Rigidと同じ固定寸法・花芯中心にしていたため、fieldの零面がcube境界で切断された断面だった。変形後の
  全componentと半径から花ごとの中心・必要範囲を求め、Marching Cubesが法線計算のため省略する外周gridを
  除いた有効領域内へ零面全体を収めるよう修正した。近接・回転確認で平らな切断面が消えた。
  証拠: [Soft sampling bounds修正後](screenshots/unified-soft-bounds-fix-20260809.png)
- **2026-08-09（花を単位として保つ）**: 作者が近接観察から次のように指摘した（原文）。

  > 形状が交差している部分がある
  > 花が形状として固定化された上での交差なら良いが要素が離れての交差はやめてほしい

  原因はSoft花弁がrest位置から大きく離れ、それでもneck fieldが花芯まで接続を作ったため、長い付け根が
  別形状を横切ったことだった。Softを自由なcomponent移動ではなく花内部の変形に限定し、花弁変位を
  softness由来の上限へclampした。さらに短い付け根をL1 collisionへ加えた。既定条件は未解決collision 0を
  保ち、平均変形は10.1%から3.3%、最大変形は16.5%になった。近接・回転・Proxy重ねで、要素が離れて作る
  長い交差が消えたことを確認した。証拠: [Soft cohesion修正後](screenshots/unified-soft-cohesion-20260809.png)

  今回止めたのは「要素の離脱が作る交差」である。固定された花field同士の厳密なfield-field交差判定までは
  主張せず、現在はguard付きmulti-sphere近似として区別する
- **2026-08-09（花一個の目視チェックポイント）**: Packingとは別URLで、3枚と4枚を同じ開き・付け根・
  花芯で大きく横並びにした。初期値では3枚は三方向へ開くまとまり、4枚は十字状のまとまりとして読める。
  開き1.18・付け根0.21・花芯0.68でもcore—petal fieldは分離せず、元の球を重ねると構成と導出面の差を
  観察できた。実座標checkbox、スライダー変更、3D回転を確認した。
  証拠: [初期3枚 / 4枚](screenshots/single-flower-3-vs-4-20260809.png)、
  [元の球との対応](screenshots/single-flower-source-overlay-20260809.png)
- **2026-08-09（横からの発見）**: 正面では花に見える一方、横から見ると現在のcomponent中心は同一平面に
  並び、全体は平たい。これは不具合として自動修正せず、次に作者が `平たい / 花弁が前へ反る / 花芯が
  盛り上がる` のどれを見たいか判断する視覚的な分岐として残す
- **2026-08-09（正解を選ばない）**: 作者は3枚 / 4枚から一つを正解として選ぶのではなく、様々な形状を
  試し、横からも観察し、自然形状をどう取り入れるかを研究の要点とした。したがってForm画面は採用案を
  決める選択器ではなく、同じ生成原理の変化を正面・横・斜めから比較し、形の系譜を増やすAtlasへ進める

実装者の画面確認は終えたが、作者自身の判断はまだである。特に、Soft の変形が「花同士の関係」に
見えるか、単に崩れた花に見えるかは作者の目視後まで未判断とする。

## Hypothesis

- 単位がRigidなら、Packingの結果は主に単位間の隙間と向きへ現れる
- 単位がSoftなら、同じ拘束が単位内部の変形へも分配されるため、被覆率だけでなく「押された履歴」が
  花弁のずれとして残る
- L0外接球はFlowerの凹部を消す。L1複数球は花弁間の隙間や噛み合いを残すが、計算増加に見合う違いかは
  目視判断が必要
- 衝突用の複数球と表示用の一体fieldを分ければ、花弁間の凹部を使ったPackingを保ちつつ、最終形だけを
  滑らかな一体物として観察できる
- Softでは単に最後にsmooth unionするだけでなく、最小neck厚または接続制約を計測しないと、見かけ上は
  接続していてもmesh化時に花弁が分離する可能性がある
- 自然らしさはランダムな凹凸を足すことではなく、枚数、成長差、曲がる方向、重力、接触、中心からの距離
  など、形が変わる理由を一つずつ動かして比較したときに観察しやすくなる

## 問答

### この後はどう進める？（2026-08-09）

作者の質問（原文）:

> この後はどう進める？
> 僕がわかるかたちと見た目の話をして

次は多数のPackingを複雑にする前に、画面を `花一個 → 花二個の接触 → 多数を詰める` の三段階へ
分ける。花一個では花弁の数・開き・付け根・中心との一体感を見る。花二個では、離れる・触れる・
重なる・溶け合うの違いを見る。その後、作者が選んだ花と接触の見え方を固定して多数を詰める。

Softは花一個の形が決まってから小さな応答として戻す。図と地の研究は別画面で並行し、Packingで生まれた
隙間を「穴」ではなくもう一方の形として左右反転表示する。型名やsolverではなく、この順番の比較画面を
作者の判断材料にする。

### 正解を選ばず、自然形状を取り入れる（2026-08-09）

作者の言葉（原文）:

> どちらが正解ではなく様々な形状を試していきたい
> 横からも観察したい
> 自然形状をどのように取り入れるかがポイントになっていきそう

3枚 / 4枚は候補の勝ち負けではなく、放射状の形が変わる最初の二点と読み直す。次のForm Atlasでは、
一つの形を正面・横・斜めから同期表示し、同時に周囲へ複数の変化を並べる。最初に増やす変化は、枚数、
平たい / 反る / 盛り上がる、花弁ごとの成長差、中心からの距離とする。

自然形状は見た目だけをランダムに歪ませて作らない。`一枚だけ少し成長が速い`、`外向きに反る`、
`重力側へ少し下がる`、`隣へ触れて押される` のように、変化の理由が見える形で加える。Seedは同じ理由の
中で個体差を見るために使い、原理の違いを隠さない。

- 形を一つに絞らず、保存した複数形と接触規則を多数Packingへ持ち込む
- 作者が Rigid / Soft と L0 / L1 を実際に回し、「関係が見えるか」を判断する
- Unified表示からFreeze用meshを生成する段階で、component数・watertightness・最小neck厚を診断し、
  現在のfield接続検査と製造用meshの一体性を区別して確認する
- neck半径とsmooth blendを作者が比較できる操作にするかは、現在の輪郭の目視判断後に決める

  field-field判定を同じ配置で比較する。作者の今回の指摘とは分けて扱う
- Soft の意味を、花弁の位置ずれだけで十分とするか、球自体の圧縮・体積保存まで進めるか判断する
- Sphere Surface の次に、作者の実SRF / imported meshを Placement Domainとして読む
- Flower以外の二つ目のMotifで同じ契約が必要になった時だけ、Motif / Domain / InstanceSetをCoreへ抽出する
- 作者がFreezeした一状態を選んだ後、Snapshot v1を固定し、別公開のHikari Adapterへ渡す
