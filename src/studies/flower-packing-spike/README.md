# 花を詰める — Flower Packing Spike

## Question

作者の要望（2026-08-09、原文）:

> katachiのSRFpackに例えば３や４の球体からなるお花をパックしてみたいと思った
>
> 上記の形状に限らずパッキングをできるようにしたい
>
> hikariが別で実装動いてるからどういうふうに進めたら良いか一緒に考えたい

形を保つ Rigid packing と、押されて変形する Soft packing の両方を見たいか確認したとき、作者は
次のように答えた（同日、原文）:

> 両方みたい

同じ Flower、同じ配置面、同じ Seed でも、単位が外部の拘束へ抵抗する場合と、応答して変わる場合で、
詰まり方・隙間・単位同士の関係はどう変わるか。単球の当たり判定と、花芯＋花弁を覚えた複数球の
当たり判定では、何が観察できるようになるか。

作者から実画面の目視後、次の問いが加わった（2026-08-09、原文）:

> 花について、いまは球体のままだけど
> 花になる形態自体は一体にできる？

できる。配置と衝突判定では花芯＋花弁の複数球を保ちながら、形態の表示・Freeze・mesh書出しでは
それらを一つの scalar field として smooth union し、連続した一体形として実体化できる。
「一体」は、見た目が滑らかにつながること、mesh が一つの watertight component になること、Softでも
花芯と花弁の接続が切れないことの三段階に分け、同じ言葉で混同しない。

## Setup

- Flower は一つの花芯球と四つの花弁球からなる。高精細な花ではなく、単位と Instance を分けるための
  最小モチーフである
- `硬さ` 比較は同じ初期配置を、左 Rigid / 右 Soft として解く。Rigid は花全体だけが移動し、Soft は
  花弁球が花芯との接続を保ちながら rest offset からずれる
- `当たり判定` 比較は両方 Rigid のまま、左 L0 外接球 / 右 L1 複数球として解く
- Domain は Plane と Sphere Surface。Sphere は位置から normal と接線二軸を作り、花を外向きに置く
- solver は seed 付き初期配置から、proxy 球の貫通を接平面方向へ押し戻す素朴な反復緩和。Soft は
  変位の一部を花弁の局所 offset へ渡し、各反復で rest shape へ弱く戻す
- Gap は solver 固有値ではなく、各 collision proxy 半径へ半分ずつ加える clearance inflation として扱う
- `比較を保存 JSON` は左右の解を保存・再読込する。`右側をFreeze` は component sphere を実体化した
  draft Snapshot を保存するが、まだ Hikari Snapshot v1 ではないことをファイル内に明記する
- `球をそのまま / 一体の花` はPacking結果を変えない表示切替。一体表示は花ごとに5球のSDFを
  smooth unionし、Softで花弁が離れても形態の接続が失われないよう花芯—花弁間の細いneck fieldを加え、
  Marching Cubesでその場の面を表示する。現段階のFreezeはまだcomponent sphereであり、このpreview meshを
  watertightな製造用meshとして保存する機能ではない
- Softは花弁ごとのrest位置からの移動量を花半径に比例した範囲へ制限し、接触解消後のpolishでも同じ制約を
  外さない。L1衝突Proxyは花芯・花弁だけでなく、短い付け根上の補助球とsmooth-union膨張分のguardを含む
- `flower-form-spike.html` はPackingを隠し、一つの選択形を正面・横・斜めの固定カメラで同期表示する。
  3〜12枚は同じ画面で切り替え、花弁の開き・付け根・花芯・自然形状の理由・元球表示だけを操作する。
  花芯なしでは隠れた中心球を残さず、隣接花弁間のneck fieldで一つの環状Motifを保つ。7枚以上では花の外径をほぼ保つため、一枚の半径を
  `sqrt(6 / petalCount)` で小さくし、枚数増加と全体巨大化を混同しない
- Form Atlasの「この形をPackingで見る」は、花弁数・花芯・開き・付け根・反り・高さ・成長差をURLで
  Packingへ渡す。Packingの`花の形`比較は左に従来の4枚花、右に選択形を置き、同じSeedから両方をRigidで
  解く。6枚花芯あり、10枚花芯なし、12枚花芯ありはPacking側からも直接選べる
- 同ページのForm Atlas下段には
  `平たい基準 / 花弁が起きる / 花芯が上がる / 育ち方が違う` の四つを同時に残す。各変化は
  cupping、core lift、petal growth differenceという原因に対応し、一般的なランダム歪みはまだ加えない

## Observation

- **2026-08-09（実装観察）**: Flower を一つの rigid unit として保持する経路と、花弁の局所 offset を
  packing pressure へ応答させる経路を、同じ初期 Instance から分岐できた。これは「花」という見た目を
  Core に入れず、Motif の response の違いとして比較できる最小形になっている
- **2026-08-09（正直な計器）**: solver が反復上限へ達しても未解決なら `Packed` と呼ばず、collision数、
  最大penetration、Domain外、平均変形とともに「部分的に配置」と表示する
- **2026-08-09（Hikari境界）**: Freeze は光学値を一切持たず、形・生成条件・scale provenance・診断だけを
  保存する。Hikari Adapter が成立するまでは draft と明記し、現在の Hikari 実装を import しない
- **2026-08-09（初回の実画面）**: Sphere Surface、Seed 304、34 flowers、size 0.25、Gap 0.025で、
  RigidとSoftはいずれも未解決collision 0まで接触を解消した。Rigidの平均変形は0.0%、Softは10.1%。
  花芯を暗く、花弁を明るく分けたことで、Soft側でも「一個の花」が崩れずに局所関係だけ変わる状態を
  追えるようになった。これは見た目の優劣ではなく、変形が実際に観察できる最低条件の確認である

  sunflower初期配置を使った。同条件でRigid/Softとも未解決collision 0、平均変形0.0%/1.1%となり、
  曲率の無い対照面でも同じ契約が働いた

  花弁それぞれの輪郭を残す。同じSeedで両方ともcollision 0へ収束し、配置の粗さの違いだけを比較できた。

  添付画像にあった平らな円盤状の面は、Softで花弁が移動しているのに、Marching Cubesのsampling cubeを

- **2026-08-09（花を単位として保つ）**: 作者が近接観察から次のように指摘した（原文）。

  > 形状が交差している部分がある
  > 花が形状として固定化された上での交差なら良いが要素が離れての交差はやめてほしい

  原因はSoft花弁がrest位置から大きく離れ、それでもneck fieldが花芯まで接続を作ったため、長い付け根が
  別形状を横切ったことだった。Softを自由なcomponent移動ではなく花内部の変形に限定し、花弁変位を
  softness由来の上限へclampした。さらに短い付け根をL1 collisionへ加えた。既定条件は未解決collision 0を
  保ち、平均変形は10.1%から3.3%、最大変形は16.5%になった。近接・回転・Proxy重ねで、要素が離れて作る
  長い交差が消えたことを確認した。証拠: [Soft cohesion修正後](screenshots/unified-soft-cohesion-20260809.png)

  今回止めたのは「要素の離脱が作る交差」である。固定された花field同士の厳密なfield-field交差判定までは
  主張せず、現在はguard付きmulti-sphere近似として区別する

## Hypothesis

- 単位がRigidなら、Packingの結果は主に単位間の隙間と向きへ現れる
- 単位がSoftなら、同じ拘束が単位内部の変形へも分配されるため、被覆率だけでなく「押された履歴」が
  花弁のずれとして残る
- L0外接球はFlowerの凹部を消す。L1複数球は花弁間の隙間や噛み合いを残すが、計算増加に見合う違いかは
  目視判断が必要
- 衝突用の複数球と表示用の一体fieldを分ければ、花弁間の凹部を使ったPackingを保ちつつ、最終形だけを
  滑らかな一体物として観察できる
- Softでは単に最後にsmooth unionするだけでなく、最小neck厚または接続制約を計測しないと、見かけ上は
  接続していてもmesh化時に花弁が分離する可能性がある
- 自然らしさはランダムな凹凸を足すことではなく、枚数、成長差、曲がる方向、重力、接触、中心からの距離
  など、形が変わる理由を一つずつ動かして比較したときに観察しやすくなる

## 問答

### この後はどう進める？（2026-08-09）

作者の質問（原文）:

> この後はどう進める？
> 僕がわかるかたちと見た目の話をして

次は多数のPackingを複雑にする前に、画面を `花一個 → 花二個の接触 → 多数を詰める` の三段階へ
分ける。花一個では花弁の数・開き・付け根・中心との一体感を見る。花二個では、離れる・触れる・
重なる・溶け合うの違いを見る。その後、作者が選んだ花と接触の見え方を固定して多数を詰める。

Softは花一個の形が決まってから小さな応答として戻す。図と地の研究は別画面で並行し、Packingで生まれた
隙間を「穴」ではなくもう一方の形として左右反転表示する。型名やsolverではなく、この順番の比較画面を
作者の判断材料にする。

### 正解を選ばず、自然形状を取り入れる（2026-08-09）

作者の言葉（原文）:

> どちらが正解ではなく様々な形状を試していきたい
> 横からも観察したい
> 自然形状をどのように取り入れるかがポイントになっていきそう

3枚 / 4枚は候補の勝ち負けではなく、放射状の形が変わる最初の二点と読み直す。次のForm Atlasでは、
一つの形を正面・横・斜めから同期表示し、同時に周囲へ複数の変化を並べる。最初に増やす変化は、枚数、
平たい / 反る / 盛り上がる、花弁ごとの成長差、中心からの距離とする。

自然形状は見た目だけをランダムに歪ませて作らない。`一枚だけ少し成長が速い`、`外向きに反る`、
`重力側へ少し下がる`、`隣へ触れて押される` のように、変化の理由が見える形で加える。Seedは同じ理由の
中で個体差を見るために使い、原理の違いを隠さない。

### 次の目視チェックポイントまで進める（2026-08-09）

作者の指示（原文）:

> つぎの目視チェックポイントまですすめて

このチェックポイントでは、一つの花を手で回さなくても正面・横・斜めが同時に見え、下段の四形から
観察する形を切り替えられるところまで進めた。四形は採用候補の順位ではなく、形が変わる理由の見本である。
作者が見る点は、`正面の輪郭を保ったまま横に厚みが生まれるか`、`花弁が起きることと花芯が上がることが
別の形として読めるか`、`成長差が自然な個体差に見えるか、単なる大小に見えるか` の三点とする。

### 花弁を増やし、花芯をオン / オフする（2026-08-09）

作者の要望（原文）:

> 花弁を5まいや6枚など増やしてみてみたい
> 花芯はオンオフ出来ても良さそう

Form Atlasの花弁数を3 / 4 / 5 / 6枚へ増やし、花芯を独立してオン / オフできるようにした。花芯を
オフにした場合も一つの花として扱えるよう、花弁は隣同士でつながる。5枚 / 6枚では中央に空きが現れるため、
見る点は花弁数の違いだけでなく、`花の表面が本体か、中央の空きも同じ強さの形として見えるか` へ広がった。

### 花弁をさらに増やして見る（2026-08-09）

作者の要望（原文）:

> 花弁をもっと増やした場合も見てみたい

Form Atlasを3〜12枚へ広げ、7 / 8 / 9 / 10 / 11 / 12枚を連続して選べるようにした。多花弁では
全体の大きさを増やすのではなく、一枚ずつを少し小さくして外径を保つ。これにより、枚数が増えたときに
輪郭の細かな反復がどの時点で一つの環・花冠としてまとまり始めるかを同じ画面で追える。

### Form Atlasの花を「花を詰める」へ適用できる？（2026-08-09）

作者の質問（原文）:

> これらを花を詰めるに適応できる？

適用できる。Form Atlasで選んだ `花弁数 / 花芯の有無 / 開き / 付け根 / 反り / 花芯の高さ /
花弁の成長差` を一つのFlower定義としてPackingへ渡す。最初は形を崩さないRigidで行い、現在の四枚花と
選択した花を同じ配置面・Seedで比較する。花芯なしでは中心を埋めるProxyを置かず、実際の花弁と隣接する
付け根だけを当たり判定に使うため、中央の空きも形の一部として残る。

Softはその次に分ける。花芯ありはcore—petal、花芯なしはpetal—petalの隣接関係を保ち、要素の離脱を
防ぐ。特に多花弁の環では、押されたときに中央の空きが潰れることを許すか、面積や穴径を保つかが新しい
観察対象になる。したがって最初のPacking目視チェックポイントは、Atlasの一形をRigidで送る、現在の
四枚花と並べる、花芯なしの穴が残るかを見る、の三点とする。

### Packingへ進めてみる（2026-08-09）

> 進めてみて

6枚・花芯あり、10枚・花芯なし、12枚・花芯ありを選べる。左の従来四枚花は対照として残し、左右とも

### 花の様々な設定をすべて引き継ぐ（2026-08-09）

花弁数と花芯だけでなく、開き、付け根、花芯サイズ、反り、花芯高さ、成長差をすべてFlower定義として

### Packingの中で全部変更できるようにする（2026-08-09）

作者の指示（原文）:

> 全部変更できるようにして

Packingの `花の形をすべて調整` を開き、花弁数、花芯、開き、付け根、花芯サイズ、反り、花芯高さ、
成長差の8項目をその場で変更できるようにした。左側の4枚花は比較の基準として固定し、右側だけが

### 花のかぶりが大きくなりすぎている（2026-08-09）

作者の観察（原文）:

> はなのかぶりが大きくなりすぎてる

11枚の環を24個、小さい間隔で球面へ置いた状態では、近づいたときに前後左右の花が重なって一つずつの
輪郭を追いにくい。まず10枚以上の花芯なしに対する初期個数を18へ下げ、花どうしの初期間隔を0.055へ
広げた。詰める量を固定する変更ではなく、見分けられる状態から観察を始めるための初期値変更である。
個数を増やして再びかぶりが生まれる境目や、間隔を狭めたときに環同士が編まれる見え方も、同じ操作で

### 花の数とは別に表面充填率で考える（2026-08-09）

作者の要望（原文）:

> 花の数はあってもよいが別案で表面充填率を考えてほしい

花の数は残すが、別の詰め方として `球面の何％が花で覆われたか` を基準にする。同じ24個でも、4枚花と
11枚の環では一個が占める面積が違うため、数だけでは形同士を公平に比較できない。表面充填率を揃える
比較では、左右を同じ個数にせず、同じ目標率とSeedから各形に必要な個数を別々に求める。

充填率は二つに分ける。

- **実体充填率**: 球面を花の白い実体が覆う割合。花芯なしの中央穴は空きとして数える。比較の主値
- **占有範囲率**: 花の外周が確保している領域の割合。中央穴も花一個の領域として含める。間隔の観察値

視点から見える面積は回転で変わるため使わない。球面上へ均等な観測点を置き、各点の法線方向に花の一体形が
あるかを判定して実体充填率を測る。画面は `個数で詰める / 充填率で詰める` を切り替え、後者では
`目標 55% / 実測 53% / 結果 18個` のように目標、実測、結果個数を同時表示する。これにより穴の多い環と
花芯ありの花を、同じ表面被覆という条件から見比べられる。

### 表面充填率を実装して確認できるようにする（2026-08-09）

作者の指示（原文）:

> 実装して確認できるようにして

Packing画面へ二つの詰め方を実装した。`個数で詰める` では従来どおり左右を同数にし、花の数を直接
変更する。`充填率で詰める` では目標率を操作し、左右それぞれが目標へ近づく花数を別々に求める。
左右の上部に `花の数 / 実体充填 / 占有範囲` を常時表示するので、どちらのモードでも数と被覆を同時に
見られる。目標20%の実画面では4枚花24個と11枚環22個がほぼ同じ実体充填になった。花芯なしの穴は
空きとして測られ、数値のために透明な中心を埋めることはしない。

### 充填率を上げ、一体形状としてプリントする（2026-08-09）

作者の要望（原文）:

> 充填率をさらに上げられるようにしたい
> ポイントは一体形状にしてプリントできるようになること

目標率の上限と花数だけを増やすと、独立した花が重なるだけでプリント可能な一体形状にはならない。
ここからは `高密度に配置される / 花同士が一つにつながる / 閉じた厚みのあるmeshになる` を別々に
確認する。特に現在の「一体の花」は一個ごとのfield接続であり、球面全体が一部品になった証明ではない。

最初の候補は二つある。

- **花だけでつながるレース状の殻**: 花芯なしの中央穴や花間の空きを貫通穴として残せる。図と地の研究に
  近いが、全花の接続、最小neck厚、watertightnessを満たすまでSTLを完成扱いにできない
- **薄い球殻を土台にして花をつなぐ**: 全花を一部品にしやすく強度も作りやすいが、中央穴の奥が球殻で
  閉じるため、現在の図地反転とは別の形になる

図と地を等価に扱うこれまでの方向から、第一案は花だけでつながるレース状の殻とする。ただしこれは結果の
意味を変える選択なので、実装前に作者が `穴を貫通させたい / 薄い土台が見えてもよい` のどちらを望むか
目視の言葉で確認する。

作者は、花だけでつながる第一案を提示した後に次のように承認した（原文）:

> はい

そこでPackingの最初の目視値を50%へ上げ、右側だけを全球同時のfieldへ変換する `プリント用レース殻`
を追加した。`つなぐ太さ / mesh細かさ / 仕上がり外径 / 必要な接続厚` は独立に変えられる。検査後は
右側がSTLと同一meshの表示へ切り替わる。花のつながりが一群、保存meshが一成分、面が閉じ、最小接続が
指定厚以上という四条件をすべて通った時だけ `STLを保存` を有効にする。設定を一つでも変えた場合は
旧検査を無効にして再検査を要求する。正面・横・斜めの定点ボタンも加え、回転操作なしで穴の貫通を確認
できるようにした。これはソフトウェア上の製造mesh検査であり、実機プリント成功の主張ではない。

### 花芯同士を細くつなぎ、内部サポートを減らす（2026-08-09）

作者の要望と指示（原文）:

> 花芯同士をなるべく細く繋いで内部にサポートが発生しないような形状について考えたい
>
> 必要であれば別研究へ移行してよい
>
> まずは考えてみて

> 設計してみて

現在のレース殻は花全体を太らせて接続するため、一体化と引き換えに花同士が溶ける。次は配置をやり直さず、
花本体を保ったまま花芯の裏側だけへ細いネットワークを加える。造形方向を持たない単なる直線接続では
水平な橋が増えるため、別Study `flower-core-network` として、`最短直線 / 表面に沿う葉脈 /
造形方向へ持ち上がるアーチ` の三形を同じ7花パッチで比較する設計にした。

第一候補はアーチ経路と造形方向へ向けた菱形断面だが、数値で自動採用しない。作者は外・内・横から、
枝が後付けの支柱に見えるか、内側の形に見えるかを判断する。全花の接続は最小全域木で一群にした後、
短い辺を加えて輪を作る。根元は太く、中央は細くし、花弁へは融合させない。

`サポート不要` は形だけで断定できないため、造形方向、物理scale、layer height、overhangとbridgeの仮値を
recipeへ含める。画面は危険下面、下層に支えられない開始領域、最長支持なし距離を**推定**として表示し、
実際の内部サポート0は作者がスライサーで確認する。詳細設計は
[Flower Core Network](../../../docs/architecture/flower-core-network-20260809.md) に固定した。
