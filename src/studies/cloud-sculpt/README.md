# S1 — 雲をこねる (Cloud Sculpt)

## Question

球の集まりは、いつ雲に見え始め、いつただの塊に堕ちるか。
そして「場をこねる」という操作は、手に馴染むか。

## Setup

- **場の定義**: 雲 = 球のリスト（中心・半径）＋ smooth-min の k。これが正本で、画面はすべてこのリストからの導出
- **SDF**: 各球の距離場 `|p - c| - r` を polynomial smooth-min で合成

  ```
  smin(a, b, k) = mix(b, a, h) - k·h·(1-h),  h = clamp(0.5 + 0.5(b-a)/k, 0, 1)
  ```

  （Inigo Quilez の定式。k=0 で通常の min = ハードな合成に退化する）
- **表示**: レイマーチング（フルスクリーンクアッドのフラグメントシェーダ）。
  マーチングキューブスではなくレイマーチを選んだ理由:
  1. 球リスト → 画面がワンパスで、こねた瞬間に絵が変わる（メッシュ再構築の待ちがない）
  2. 実装が小さい（メッシュ化はメッシュ出力が要る T3 で必要になったときに作る）
  3. トレードオフ: 球数の上限（現在 64、シェーダのユニフォーム配列）と、
     メッシュが存在しないこと（輸出は不可。これは T3 の仕事）
- **二つの手**:
  - つまみ = 球数／半径／半径のばらつき／ブレンド k／シード（スライダー＋数値。`k` は即時反映、球数・半径・ばらつき・seed はその場で再生成）
  - こねる = クリックで球の追加（何もない場所）・選択（雲の上）、選択中の球をドラッグで移動
    （カメラに正対する平面上を動く）、Delete で削除。カメラはオービット
- **ピッキング**: CPU 側で同じ fieldSdf をレイマーチ（見えているものとクリックできるものが必ず一致）
- **手の履歴**: 全操作を `[{t, op, args}]` で記録。op = grow / setParam / addBall / removeBall / moveBall / clear。
  JSON 書き出し・読み込みで同じ形が再現される（replay はエントリ列以外の状態に依存しない）
- **技術選定**: vite + three.js + 素の TypeScript（フレームワークなし）。
  three.js はカメラ・レイ・シェーダの土台として。UI が 1 パネルだけなので React は過剰と判断

### 起動・ビルド

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # 型チェック + dist/ 生成
```

### 応答速度（実測）

- 確認環境: isolated Chrome headless + software WebGL
- `count` スライダー変更から次フレームまで: 約 `1.1 ms`
- `exportJson()` → `importJson()` → 次フレームまで: 約 `811 ms`
- headless verification では fps 表示は `~1 fps` 付近だった（本番のデスクトップ実機では再計測する）

## Observation

- **2026-07-03**: isolated Chrome で初期画面を開くと、Version/UpdatedAt と操作パネルが表示された。`count` を変えると雲はその場で再生成され、`exportJson()` → `importJson()` で球の並びが完全一致した。空白クリックで球を追加でき、Delete で削除できた。選択中の球はドラッグで位置が変わり、`moveBall` が履歴に残った。

## Hypothesis

- 雲らしさは球のリストではなく「輪郭の柔らかさの分布」に宿るのではないか。
  同じ球数でも k と半径のばらつき次第で雲にも塊にもなる
