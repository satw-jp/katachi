# S1 — 雲をこねる (Cloud Sculpt)

## Question

球の集まりは、いつ雲に見え始め、いつただの塊に堕ちるか。
そして「場をこねる」という操作は、手に馴染むか。

## Setup

- **場の定義**: 雲 = 球のリスト（中心・半径）＋ smooth-min の k。これが正本で、画面はすべてこのリストからの導出
- **SDF**: 各球の距離場 `|p - c| - r` を polynomial smooth-min で合成

  ```
  smin(a, b, k) = mix(b, a, h) - k·h·(1-h),  h = clamp(0.5 + 0.5(b-a)/k, 0, 1)
  ```

  （Inigo Quilez の定式。k=0 で通常の min = ハードな合成に退化する）
- **表示**: レイマーチング（フルスクリーンクアッドのフラグメントシェーダ）。
  マーチングキューブスではなくレイマーチを選んだ理由:
  1. 球リスト → 画面がワンパスで、こねた瞬間に絵が変わる（メッシュ再構築の待ちがない）
  2. 実装が小さい（メッシュ化はメッシュ出力が要る T3 で必要になったときに作る）
  3. トレードオフ: 球数の上限（現在 64、シェーダのユニフォーム配列）と、
     メッシュが存在しないこと（輸出は不可。これは T3 の仕事）
- **二つの手**:
  - つまみ = 球数／半径／半径のばらつき／ブレンド k／シード（スライダー＋数値。`k` は即時反映、球数・半径・ばらつき・seed はその場で再生成）
  - こねる = クリックで球の追加（何もない場所）・選択（雲の上）、選択中の球をドラッグで移動
    （カメラに正対する平面上を動く）、Delete で削除。カメラはオービット
- **ピッキング**: CPU 側で同じ fieldSdf をレイマーチ（見えているものとクリックできるものが必ず一致）
- **手の履歴**: 全操作を `[{t, op, args}]` で記録。op = grow / setParam / addBall / removeBall / moveBall / setBallRadius / clear。
  JSON 書き出し・読み込みで同じ形が再現される（replay はエントリ列以外の状態に依存しない）
- **選択中の球の個別編集**: 球を選ぶとパネルに「選択中の球」エディタが現れる。
  半径スライダー（`setBallRadius` を記録）と X/Y/Z の数値入力（`moveBall` を記録、ドラッグより正確）。
  つまみ（場全体の生成パラメータ）とは別の、一球ごとの手
- **技術選定**: vite + three.js + 素の TypeScript（フレームワークなし）。
  three.js はカメラ・レイ・シェーダの土台として。UI が 1 パネルだけなので React は過剰と判断
- **3D データ書き出し（T3 第一便）**: パネルの「3Dデータ」で最長辺 mm と解像度を指定し、
  「メッシュを検査」で三角形数・mm バウンディングボックス・水密性を表示、「3Dデータで書き出す」で
  STL/OBJ/同名 `.recipe.json` を同時に保存する。書き出しは導出なので履歴には積まない。
  メッシュ化は `fieldSdf`（画面・ピッキングと同じ smooth-min）を格子サンプルし、各キューブを
  6つの四面体へ分割して等値面 0 を三角形化する marching tetrahedra 方式。
  T3 指示書の「古典的な 256 ケース marching cubes」より小さい表で済む第一便の実装として採用した。
  出典: Lorensen & Cline, "Marching Cubes" (1987) の等値面抽出の系譜、および marching tetrahedra の
  立方体分割法。厳密な 256 ケース表への置換は、解像度/三角形数の比較が必要になった時点で行う。
- **水密検査**: 生成三角形の各エッジを量子化した頂点キーで集計し、全エッジがちょうど2枚の三角形に
  共有されるかを見る。`openEdges=0` かつ `nonManifoldEdges=0` のときだけ水密 OK と表示する。

### 起動・ビルド

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # 型チェック + dist/ 生成
```

### 応答速度（実測）

- 確認環境: isolated Chrome headless + software WebGL
- `count` スライダー変更から次フレームまで: 約 `1.1 ms`
- `exportJson()` → `importJson()` → 次フレームまで: 約 `811 ms`
- headless verification では fps 表示は `~1 fps` 付近だった（本番のデスクトップ実機では再計測する）

  加えて Codex が未検証だった**法線の向き**を符号付き体積（発散定理）で確認 — 正値（+2.201）で

- **2026-07-10（作者実機で発見 → 修正）**: 作者報告「S1 の画面と STL が違う（しぶきが画面に出ない、
  データと STL は合っている）」。原因はシェーダの表示上限 MAX_BALLS=64 — MPM 凍結レシピ（151球）の
  65球目以降が**画面にだけ**出ていなかった（STL/検査/ピッキングは CPU 側で全球処理）。
  「見ているものと出力されるものが一致する」の原則が球数の崖で破れていた。
  修正: MAX_BALLS を 256 へ（ループは uBallCount で早期 break、少球時のコストは不変）。
  さらに 256 超過時は選択情報欄に「⚠ 画面は最初の256球のみ表示」と正直に警告（300球の合成レシピで検証済み）。
  151球の凍結レシピは全球表示・水密 OK を確認。

## Hypothesis

- 雲らしさは球のリストではなく「輪郭の柔らかさの分布」に宿るのではないか。
  同じ球数でも k と半径のばらつき次第で雲にも塊にもなる
