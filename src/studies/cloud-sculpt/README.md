# S1 — 雲をこねる (Cloud Sculpt)

## Question

球の集まりは、いつ雲に見え始め、いつただの塊に堕ちるか。
そして「場をこねる」という操作は、手に馴染むか。

## Setup

- **場の定義**: 雲 = 球のリスト（中心・半径）＋ smooth-min の k。これが正本で、画面はすべてこのリストからの導出
- **SDF**: 各球の距離場 `|p - c| - r` を polynomial smooth-min で合成

  ```
  smin(a, b, k) = mix(b, a, h) - k·h·(1-h),  h = clamp(0.5 + 0.5(b-a)/k, 0, 1)
  ```

  （Inigo Quilez の定式。k=0 で通常の min = ハードな合成に退化する）
- **表示**: レイマーチング（フルスクリーンクアッドのフラグメントシェーダ）。
  マーチングキューブスではなくレイマーチを選んだ理由:
  1. 球リスト → 画面がワンパスで、こねた瞬間に絵が変わる（メッシュ再構築の待ちがない）
  2. 実装が小さい（メッシュ化はメッシュ出力が要る T3 で必要になったときに作る）
  3. トレードオフ: 球数の上限（現在 64、シェーダのユニフォーム配列）と、
     メッシュが存在しないこと（輸出は不可。これは T3 の仕事）
- **二つの手**:
  - つまみ = 球数／半径／半径のばらつき／ブレンド k／シード（スライダー＋数値。`k` は即時反映、球数・半径・ばらつき・seed はその場で再生成）
  - こねる = クリックで球の追加（何もない場所）・選択（雲の上）、選択中の球をドラッグで移動
    （カメラに正対する平面上を動く）、Delete で削除。カメラはオービット
- **ピッキング**: CPU 側で同じ fieldSdf をレイマーチ（見えているものとクリックできるものが必ず一致）
- **手の履歴**: 全操作を `[{t, op, args}]` で記録。op = grow / setParam / addBall / removeBall / moveBall / setBallRadius / clear。
  JSON 書き出し・読み込みで同じ形が再現される（replay はエントリ列以外の状態に依存しない）
- **選択中の球の個別編集**: 球を選ぶとパネルに「選択中の球」エディタが現れる。
  半径スライダー（`setBallRadius` を記録）と X/Y/Z の数値入力（`moveBall` を記録、ドラッグより正確）。
  つまみ（場全体の生成パラメータ）とは別の、一球ごとの手
- **技術選定**: vite + three.js + 素の TypeScript（フレームワークなし）。
  three.js はカメラ・レイ・シェーダの土台として。UI が 1 パネルだけなので React は過剰と判断
- **3D データ書き出し（T3 第一便）**: パネルの「3Dデータ」で最長辺 mm と解像度を指定し、
  「メッシュを検査」で三角形数・mm バウンディングボックス・水密性を表示、「3Dデータで書き出す」で
  STL/OBJ/同名 `.recipe.json` を同時に保存する。書き出しは導出なので履歴には積まない。
  メッシュ化は `fieldSdf`（画面・ピッキングと同じ smooth-min）を格子サンプルし、各キューブを
  6つの四面体へ分割して等値面 0 を三角形化する marching tetrahedra 方式。
  T3 指示書の「古典的な 256 ケース marching cubes」より小さい表で済む第一便の実装として採用した。
  出典: Lorensen & Cline, "Marching Cubes" (1987) の等値面抽出の系譜、および marching tetrahedra の
  立方体分割法。厳密な 256 ケース表への置換は、解像度/三角形数の比較が必要になった時点で行う。
- **水密検査**: 生成三角形の各エッジを量子化した頂点キーで集計し、全エッジがちょうど2枚の三角形に
  共有されるかを見る。`openEdges=0` かつ `nonManifoldEdges=0` のときだけ水密 OK と表示する。
- **Hikari 観察ビュー**: 画面上部の `KATACHI / HIKARI` で、ファイルを介さず同じ球リスト・smooth-min k・
  カメラを観察表現へ切り替える。現在の場から Seed 固定で粒子を生成し、`Points / Trails / Density` と
  `Surface / Inside` を切り替えられる。粒子数、速さ、渦、軌跡の長さ、粒子サイズ、露光、にじみは
  ブラウザ上で即時反映し、設定と最後に開いた画面は `localStorage` に保持する。Python/CUDA/外部APIは使わない。
  Surface は球から得た候補を同じ `fieldSdf` のゼロ面へ反復投影する。Inside は球の体積を重みとした近似で、
  smooth-min 合成体に対する厳密な一様サンプルではないことを画面にも明記する。
- **Hikari baseline case v0.17.1**: HIKARI の「この景色を保存」は、再生可能な形状レシピ、全Hikari設定、

  画素は保存しないため、これはレンダー出力ではなく比較・再訪用の基準ケースである。

  `1 mm / shape-unit` は `assumed` であり実物寸法ではない。この契約は次の材料接続の準備で、現行Hikariの
  scalar吸収、renderer、shader、CPU/WebGPU光線計算には未接続である。

  追加した。WebGLの視線と透明影は解析的な球交差で内包を扱い、内包が外側に収まらない場合はhostだけへ戻して警告する。

  これは最終的な造形制限ではない。次はseed付きの複数・不均一サイズ・soft-cluster内包へ一般化する。

- **WebGPU inclusion focused light v0.18.2**: WebGPU光線もCPUと同じscene adapterで一個の球状内包を検証し、

- **共有受光HDR場 v0.22.0**: 集光を毎フレーム最明部へ合わせる8-bit画像ではなく、`OpticalScene.receiver`を

- **WebGPU Optics v0.7**: Hikari Opticsの平行光線とSDF交差、入射／出射屈折をraw WebGPU computeへ

  現段階は交差・屈折だけがGPUで、結果はCPUへ読み戻してThree.jsの点／線へ組み直す。したがって標本数を
  極端に増やしたときの最終上限はreadbackとCPU側の可視化であり、完全なGPU内蓄積ではない。
- **有限光源と透過影 v0.8**: Naturalの受光面は単一方向の0/1遮蔽をやめ、光源の角度的な広がりに応じて
  3／5／9方向をSDFへ照射する。各方向について透明形状内を進んだ距離を近似し、Beer–Lambert型の減衰と
  2界面のFresnel透過を合成する。これにより、届いた方向の割合による半影、厚みによる影の濃淡、
  素材色に応じた透過色が同じ影へ現れる。`光源の広がり °` は0.1〜30°。晴天の太陽の見かけ直径約0.53°を
  基準とし、大きい値は雲・窓・拡散材などで光源が広がった状態を比較する近似であって、
  厳密な全天空照明ではない。AnalysisとWebGPU光路計算は従来どおり独立して残す。
- **表面・内部・屈折環境 v0.9**: Naturalの背景は無限遠の方向環境として扱い、屈折後の出射方向で
  空・地平線・樹木状の明暗を参照する。形状の中では方向が変わるため模様が湾曲するが、カメラ移動によって
  背景距離や地平線がずれることはない。有限距離として扱うのは形状と受光床だけ。
  `屈折率`で歪み、`環境の回転 °`で映り込みとの対応を比較できる。
  `表面の粗さ`は反射・屈折の周囲を3／5方向で近似積分し、`表面の揺らぎ`はSDF法線へ小さな変化を加える。
  `内部のむら`と`むらの大きさ`は分離した3D材料場として、形状本体の吸収と透過影の光学距離へ同時に反映する。
  ハイライトは粗さを使うGGX近似へ変更した。これはリアルタイムな比較モデルであり、HDRI、経路追跡、
  多重内部反射、編集可能な材料ボリュームはまだ備えない。
- **床照度場・靄・白黒 v0.10**: WebGPU／CPUが求めた床到達点を128角の照度テクスチャへ蓄積し、
  Naturalの床材シェーダー内で参照する。従来の前景オーバーレイをNaturalでは非表示にしたため、
  形越しに見える光溜まりは床模様と同じ出射光線でもう一度屈折する。遠方の床は距離霧で空の色へ収束し、
  地平線付近の風景ディテールも`靄`で減衰する。`color / mono`は最終光学出力を切り替え、
  monoでは素材色より光量・影・集光の構造を優先して観察する。
- **波長分散 v0.11**: `プリズム`は緑の中心光路に対して赤の屈折率を少し下げ、青を少し上げる。
  形越しの無限遠環境はRGBごとに異なる出射方向を参照し、床へ届く光も屈折偏向の方向へRGBをずらして
  128角の照度場へ蓄積する。したがって形の縁だけでなく、床の集光にも色の分離が現れる。
  低い値はレジンらしい微細なずれ、上半分は分離方向を学ぶための観察的な誇張である。
  現在は中央の緑光路で求めた一つの出射点をRGBで共有し、赤／青の環境方向と床到達分布を近似する。
  連続スペクトル、多重内部反射、薄膜干渉、応力複屈折を解く物理レンダーではない。
- **局所虹 v0.12**: `虹の出方 local / global`を追加。globalはv0.11の形全体へ広がる表現をそのまま残す。
  localは、入射から出射までの方向変化、入口と出口の法線差、斜め入射が重なる画素だけ形越しのRGB分散を
  立ち上げる。床照度場も、平行光から大きく偏向した到達光だけRGB位置を分け、偏向の弱い光は三色を
  同じ位置へ重ねて中立色に戻す。手描きマスクではなく、形・視点・光角度の関係で発生場所が移動する。
  localは幾何光学的な局所化の第一近似であり、硬化収縮から応力テンソルを求める複屈折モデルではない。
- **5帯域Prism・Stress v0.13**: PrismをRGB三本から赤・橙・緑・青緑・青の5帯域へ変更。
  均質な光では5色を中立色へ正規化し、帯域ごとに参照した環境光の差だけを色として強める。
  床照度場も5つの位置へ連続的に蓄積するため、細い赤青縁ではなく幅のある低彩度グラデーションになる。
  `虹のしくみ prism / stress`を追加し、Stressでは球殻が競合する接合部、内部光路の長さ、材料むらを
  硬化応力の代理場として使う。5波長の位相遅れから干渉色を作り、`偏光 0`では色が消える。
  `硬化応力`は位相量、`偏光`は見える強さを操作する。これは形と材料を学ぶための探索モデルであり、
  収縮率・ヤング率・境界条件から応力テンソルを解く有限要素解析ではない。
- **Prism + Stress v0.14**: `虹のしくみ prism / stress / both`を追加。bothは同じ透過光に対して、
  先に5帯域Prismの出射方向と色を求め、その結果へStressの位相遅れと偏光強度を重ねる。
  床の光溜まりはPrismの分散を保持し、形の接合部・厚い領域にはStressの干渉帯が追加される。
  bothで`偏光 0`にするとStressだけが消え、Prismは残るため、二現象の寄与を連続的に比較できる。
- **透明影・集光 v0.15**: 床の影を、直接光だけでなく透明体が失わせる環境光の濃淡として残す。
  光溜まりの有限照度テクスチャには空の余白、外周フェード、丸い支持領域を持たせ、矩形の境界を床へ
  投影しない。集光のピークだけを圧縮するため、明るい焦点と暗い透明影を同時に観察できる。
  Windows安全版は56光線の疎な到達点を広めに補間し、角張った光の斑点を抑える。
- **MPM形態変形プレビュー v0.29.0**: HIKARIの`形態変形`から既存のMLS-MPMを開始し、低頻度で
  最大220球の粗いプロキシへ凍結して同じ透明素材表示へ渡す。`止めてこの形を採用`は、その瞬間の球を
  `clear`と明示的な`addBall`履歴として固定する。シミュレーション過程はGPU／CPUの加算順まで同一とは
  主張しないが、採用した作品形状はMPMを再実行せず`.hkr`から同じ形で開ける。変形中はProgressive Renderを
  無効にし、重い受光面transportも停止してRealtime BODYだけを更新する。開始時は正式にOPTICSへ切り替え、
  入力は3,000粒子上限へ密度配分し、
  MPM領域外の形は割当前に拒否する。採用後に受光面と静止画計算へ戻す。連続MPM表面や光学計算との
  一体化ではなく、8月映像制作の第一便である。
- **高DPI録画時の自動回転 v0.29.0**: 自動回転またはMPM再生中だけリアルタイム描画の内部解像度を
  最大1xへ抑え、停止時に端末本来の最大2xへ戻す。MacのRetina画面収録でシェーダ描画と録画処理が
  同じGPUを奪い合う範囲だけを軽くする対策で、devicePixelRatioが1のWindows表示とSAFE表示は変えない。
