# S2c — 本物を混ぜる (MPM)

*v0.1.0（2026-07-10, T2d）: RESEARCH v3 Y6「驚きの源泉=本物の原理」の発注に応え、S1 の雲を
MLS-MPM（Material Point Method）の材料点として撒き、Neo-Hookean 弾性固体 ⇄ 弱圧縮粘性流体を
一本の「相」つまみで行き来する。実装は CPU TypeScript（理由は Setup 参照、WebGPU ではない）。*

*v0.2.0（2026-07-10, T2e）: WebGPU compute バックエンドを追加。物理は不変（`sim.ts` の CPU 実装が
そのまま WGSL への移植元・検算基準）。起動時に能力検出して自動選択、WebGPU 非対応環境では
CPU に自動フォールバック、手動切替もできる。現在のバックエンドは画面に常時表示。詳細は
下記 Setup「WebGPU バックエンド」と Observation を参照。*

*v0.3.0（2026-07-11, T2f）: RESEARCH §3「入口 = 既存メッシュ/NURBS の SDF 化（過去作を輸入して
余白を測る）」の回収。バイナリSTLを読み、メッシュ内側をボクセル充填してこの Study の粒子として
撒く（`stlImport.ts`）。球化・メディアル軸抽出はしない — それは既存の「凍らせる」の仕事
（T2f-import-stl.md「最小負荷の設計」）。新規実装は「STLを読む」＋「メッシュの内側を粒子で満たす」
の二点のみ。これで STL → 粒子 → （流す/流さない）→ 凍結 → S1 → 編集・STL再出力、が既存機構だけで

## Question

弾性論・流体力学という「本物の理論」を形態形成の原理として持ち込むと、作者と実装者が
入れていない振る舞い（しわ・座屈・ちぎれ・とぐろ・指状不安定）が、原理の側から立ち上がるか。
S2b（バネの素描、静的な緩和解）には構造的に出せない、時間積分された本物の力学的な挙動
（弾み・オーバーシュート・慣性）が、この Study では見えるか。

## Setup

- **場の定義**: S1 の `Ball[]`（`cloud-sculpt/field.ts`、import のみ・コピーしない）が種。
  S2/S2b と異なり、この Study 自身の「正本」は材料点（`MpmParticle[]`）— 球のリストではなく
  数千個の質点の集まりで、S1/S2/S2b の SDF・バネ網とは全く別の場の表現になる
  （T2d-mpm.md がこの Study だけに許した新しい記述形式）
- **技術選定 — CPU TypeScript、WebGPU ではない**（T2d-mpm.md §「対象環境」が明示的に許可した
  フォールバック）: 検証環境（`.claude/launch.json` の `yohaku-verify`、隔離 headless Chrome）で
  WebGPU compute の可用性・挙動を安定して検証できる保証がなく、一セッションで
  「WebGPU compute シェーダの実装 + 検証」まで届かせるのはリスクが高いと判断した。
  代わりに MLS-MPM の核（P2G→格子更新→G2P）を素の TypeScript の CPU ループとして書いた。
  副産物として: JS は単一スレッド・固定順序で加算するため、この実装は実は**決定的**
  （GPU の加算順不定という T2d-mpm.md §3 が想定した問題がそもそも起きない）。
  それでも設計は §3 の指示どおり「freeze は焼き付け結果を引数に明示的に持つ」形を採用した
  （下記「履歴と決定性」）— 将来 WebGPU に置き換えても正本の再現性が壊れないようにするため
- **格子とタイムステップ**: `sim.ts`。格子解像度 `gridN`（既定 48、48³=110,592 セル）、
  ドメインは世界座標で x,z∈[-4,4]・y∈[0,8] の固定 8×8×8 立方体（`DOMAIN_SIZE=8`）。
  二次 B-spline カーネル（Hu et al. 2018 / taichi mpm88 と同じ核）は各粒子の周囲 3×3×3
  セルを読むため、境界から `BOUND=3` セルぶんは実質的な壁（貫入禁止・側面/天井は反射、
  床は摩擦つき貫入禁止）にしている。**この結果、シミュレーション上の「床」は世界座標
  y=0 ではなく `y = BOUND×dx`**（既定格子で 0.5）— レンダラーの地面もこの高さに合わせた
  （`sim.ts` の `marginWorld()`、`renderer.ts` の `setGridResolution()`）。固定タイムステップ
  `DT = 1/6000`秒（チューニング中、より大きな dt では発散する設定があった — 具体的な閾値は
  未探索、6000 分割は安定と分かっている値をそのまま採用した保守的選択）
- **種まき**（`seeding.ts` の `seedParticlesFromBalls`）: 球ごとに独立に、球内部で
  棄却法サンプリング。密度つまみ `particlesPerUnitVolume`（既定150）× 球体積で個数を決め、
  各粒子の質量は「球の全粒子質量の合計 = 密度 × 球の体積」になるよう配分（質量保存）。
  **S1 の `growBalls()` は y<0 になりうる**（S1/S2/S2b は硬い床を前提にしないため）が、
  MPM の格子は y=0 起点の有限箱なので、種まき時に球群全体を剛体的に持ち上げて
  最下点が床（`marginWorld`）の少し上に来るようにしている（`main.ts` の
  `liftAboveGround()` — この持ち上げ後の球が実際に履歴の `seed` op の引数に記録される、
  隠れた実行時調整ではない）
- **構成則が相のつまみ**（`sim.ts` の `computeCauchyStress`、T2d-mpm.md §1 の核心）:
  一つの `phase`（0=固体端..1=流体端）が、二つの**本物の**構成則をブレンドする。
  どちらも SVD を使わない定式化を選んだ（taichi mpm88 の corotated モデルは SVD が要るが、
  実装を簡潔に保つため、SVD 不要な等価な公式を採用— 下記「試して捨てた設計」参照）:

  **固体端 — 圧縮性 Neo-Hookean**（Bonet & Wood, *Nonlinear Continuum Mechanics for
  Finite Element Analysis*, 2nd ed. の定式化系列、複数の MPM 弾性チュートリアルで
  そのまま使われる形）:
  ```
  σ_solid = (μ/J)(F Fᵀ - I) + (λ/J) ln(J) I
  μ = E / (2(1+ν))，λ = E ν / ((1+ν)(1-2ν))   [Lamé定数]
  ```
  E=ヤング率 (Pa)、ν=ポアソン比、F=変形勾配、J=det(F)。

  **流体端 — 弱圧縮性ニュートン流体**:
  ```
  σ_fluid = -p I + 2 μ_f D
  p = K (1/J - 1)，D = sym(C) = (C + Cᵀ)/2
  ```
  K=体積弾性率 (Pa)、μ_f=粘性係数 (Pa·s)、C=APIC/MLS-MPM のアフィン速度行列
  （Jiang et al. 2015 "The Affine Particle-In-Cell Method" — MLS-MPM の再構成上、
  局所速度勾配 ∇v の近似として C がそのまま使える）。p の式は弱圧縮 SPH/MPM 流体の
  典型（例: Ram et al. 2015、Fang et al. 2019 は γ=7 程度の Tait 型 `K((J^-γ)-1)` を使うが、
  この Study は簡略化した γ=1 の線形版を使用 — 正直に「簡略化」と明記する）。
  D の項も本来の粘性応力が引く偏差項 `-(2/3)tr(D)I` を省略している（既知の簡略化）。

  ブレンド: `σ = σ_solid + (σ_fluid - σ_solid) × phase`（成分ごとの線形補間）。
  Kirchhoff 応力 `τ = J σ` を、MLS-MPM の標準的な P2G アフィン項
  `stress = -dt·Vp0·(4/dx²)·τ`、`affine = stress + mass·C` に渡す（Hu et al. 2018）。

  **変形勾配の相ブレンド**（本 Study 独自の簡略化、教科書の標準ではない — 正直に明記）:
  各 G2P で `F_raw = (I + dt·C) F_old`（標準更新）の後、`J=det(F_raw)` から
  等方版 `F_iso = J^(1/3) I` を作り、`F_new = F_raw + (F_iso - F_raw)×phase` で
  実際に保持する F を決める。phase=1 で F は毎ステップ体積のみを追う等方テンソルに
  リセットされ続ける（＝形の記憶を持たない、taichi mpm88 の「liquid material は F を
  等方にリセットする」という設計思想と同じ動機だが、離散切り替えでなく phase で
  連続的にブレンドしている点がこの Study の実装）。この F ブレンドと上の応力ブレンドは
  **独立**（同じ phase 値を使うが別々の場所で効く）
- **境界条件・摩擦**: 床は貫入禁止＋速度に 0.7 倍の摩擦（物理的に較正した摩擦係数ではなく、
  sag.ts の `SOFTNESS_STIFFNESS_FLOOR` と同種の「表示の安定のための」経験値）。
  側面・天井は反射（外向き速度を 0 にする）
- **凍らせる**（`seeding.ts` の `freezeParticlesToBalls`）: 粒子群を粗いビン（一辺
  `3×dx`）に量子化し、各ビンの粒子群を「重心位置・(質量合計/密度)=等価体積の球」1個に
  変換する（T2d-mpm.md §2 が明示的に許した粗い変換）。最低2粒子未満のビンは捨てる
- **履歴と決定性**（`history.ts` の doc コメントに詳細、T2d-mpm.md §3 の確定設計に
  従った）: 操作は `seed`（種まき、球リストと物理パラメータを明示的に記録）・
  `setParam`・`run`（サブステップ数を明示、再生時は実際に再シミュレートする —
  CPU 実装は決定的なので厳密に同じ結果になる）・`freeze`（**焼き付け結果の球リストを
  引数に明示的に持つ** — sag.ts の freeze が正本と softness から都度再計算する「暗黙の
  純関数」だったのと対照的に、こちらは結果そのものを保存する。理由: GPU 実装に将来
  置き換わっても正本の再現性が実装に依存しないようにするため、という T2d-mpm.md の
  確定判断をそのまま踏襲した）。**自動実行の履歴節約**: 「自動実行」チェックボックスは
  毎フレーム物理を進めるが、毎フレーム履歴に書かない — フレームごとに直接
  `state.particles` を進め、チェックを外した時点（または他の操作をする直前）に
  蓄積したステップ数を1件の `run` エントリとしてまとめて記録する（`main.ts` の
  `flushAutoRun()`）。物理は同じ `substep()` の逐次適用なので、まとめて記録しても
  再生結果は完全に一致する（下記 Observation で実証）
- **表示**: `renderer.ts`、THREE.Points の点描（T2d-mpm.md §2 が明示的に許可した第一段）。
  色は相（固体=珊瑚色寄り・流体=水色寄り）+ 速度でわずかに明るくする、という
  純粋に見た目のためのイラストレーティブな配色 — Y6 の役割分離により、この Study では
  余白の計器色を**混ぜない**（T2d-mpm.md「やらないこと」）
- **常設バナー**: 「MLS-MPM による連続体の近似。格子解像度と時間刻みに依存する。
  実物の保証はしない。構成則: Neo-Hookean 弾性固体 ⇄ 弱圧縮粘性流体（式は README 参照）。
  CPU 実装（実測は README）。」
- **入り口**: `mpm.html`（`vite.config.ts` に追加）。S1・S2b から「S2c 本物を混ぜる (MPM) →」、
  S2c から「← S2b たわむ」「← S1 雲をこねる」

- **WebGPU バックエンド（T2e, `src/studies/mpm/gpu/`）**: `sim.ts` の CPU 実装（P2G→格子更新→G2P、
  二次 B-spline カーネル、APIC/MLS-MPM アフィン転送、相ブレンドの構成則）を **そのまま** WGSL に
  移植した。物理式・定数（`DOMAIN_SIZE`・`BOUND`・`DT`・摩擦係数0.7など）は一切変えていない —
  移植であって改造ではない（T2e §2 の指示どおり）。CPU 実装は削除せず、①WebGPU 非対応環境の
  フォールバック、②検算の基準、の二役で残している。
  - **能力検出と自動選択**（`gpu/capabilities.ts`）: 起動時に `navigator.gpu.requestAdapter()`→
    `requestDevice()` を一度だけ試す（結果はモジュール内でキャッシュ）。成功すれば
    バックエンドは自動的に `webgpu` になる（T2e「能力検出で自動選択」）。失敗（`navigator.gpu`
    が無い、アダプタが取れない等）は例外を投げず `null` を返し、`cpu` のまま動く。
    画面左上のバッジ（`.backend-badge`）に現在のバックエンドとアダプタ名を常時表示し、
    パネル内のラジオボタンで CPU⇄WebGPU を手動切替できる（GPU 未対応環境では WebGPU 側は
    disabled）。バックエンドは履歴に**乗せない**（`history.ts` は一切変更していない —
    正本・op は完全に不変）。バックエンド切替時は `readBackFull()` で GPU 側の最新状態を
    CPU ミラー（`state.particles`）へ同期してから切り替えるため、切替の瞬間に速度・変形が
    リセットされて見えることはない（実座標クリックで確認、Observation 参照）。
  - **P2G の散布は固定小数点 atomics**（T2e §3 の指示どおり）: WGSL/WebGPU には `atomicAdd<f32>`
    が無い（i32/u32 のみ）ため、質量・運動量を `value * SCALE` を丸めた整数として
    `atomicAdd<i32>` で加算し、格子更新パスで `f32(raw) / SCALE` に戻す
    (`gpu/gpuSim.ts` の `MASS_FIXED_SCALE`/`MOM_FIXED_SCALE`、いずれも 1e6 — このStudyの
    sketch-scale の質量・運動量の大きさに合わせた仮決めで、一般解ではない。i32 の範囲
    ±2.147e9 に対し十分な余裕があることを実測レンジで確認したのみ、理論的な上限保証はない
    ことを正直に記録する)。
  - **ワークグループ構成**: 全カーネル `@workgroup_size(64)` の1次元ディスパッチ。粒子系
    （P2G・G2P）は粒子数、格子系（clear・grid update）は `gridN³` セル数に対して
    `ceil(n/64)` グループを起動する。
  - **行列の受け渡しは独自の平坦配列規約**（`gpu/shaders.ts` 冒頭のコメント参照）:
    F・C は `array<f32,9>`（`mat3.ts` の `Mat3` と完全に同じ行優先の並び）としてバッファに
    置き、シェーダ内で `mat3x3<f32>`（WGSL ネイティブは列優先）へ組み立て直してから
    `+`/`*`/`transpose()`/`determinant()` を使う。WGSL の `mat3x3` のホスト共有メモリ
    レイアウト（列ごとに16バイトパディング）には一切依存しない設計 — 実装コストは増えるが
    パッキングmiss のリスクを避けるため（詳細はコード冒頭のコメント）。
  - **パラメータは storage ではなく uniform バッファ**（実装中に発見・修正した設計判断、
    下記 Observation 参照）: P2G は粒子SoA6本＋格子atomics2本で既にstorageバインディングを
    8本使っており、WebGPU が全実装に保証する `maxStorageBuffersPerShaderStage` の下限
    （8）ちょうどに達する。`params` を storage の9本目として置くと、8までしか保証されない
    環境で `createComputePipeline` が（例外を投げずに）検証エラーとなり、パイプラインが
    実質無効になる — この開発機のアダプタは10まで許すため実害はなかったが、他アダプタでの
    破綻を避けるため `params` は uniform バッファに移した（storage の本数カウントに入らない）。
  - **描画のデータフロー — 読み戻しは「頻度」で使い分ける**（T2e §4「転送コストを実測してから
    判断」）: three.js は `WebGLRenderer` のまま（WebGPURenderer への全面置き換えはやらない —
    T2e「やらないこと」）なので、WebGPU の計算結果を GPU バッファのまま WebGL に直接渡す経路は
    無く、どこかで CPU 読み戻しが要る。実測（下記 Observation）の結果、**全状態
    （位置・速度・F・C, 粒子あたり24 floats）の読み戻し**は 3k〜100k粒子で 1〜13ms
    と軽いので、「実行」ボタン・凍結・バックエンド切替のような**離散的な操作**では
    毎回フル読み戻しをして正確さを優先する。一方**自動実行（毎フレーム）**は位置だけ
    （粒子あたり3 floats）を読み戻し、速度・F・Cは古いまま（`gpuDirty`フラグで追跡）にして、
    自動実行が止まった時・凍結の前・CPUへの切替の前に `ensureFullGpuSync()` で追いつかせる。
    ただしこの読み戻し自体の「単発コスト」は軽くても、**rAFループの中で毎フレーム行うと
    この検証環境では重く**なることを実測した — 詳細と数字は Observation、対策として
    自動実行時の GPU チャンクサイズを大きくした（`main.ts` の `tick()`）。

- **STL取り込み（T2f, `stlImport.ts`）**: 「作業負荷が一番少ない方法」（作者の言葉）としてこの Study
  の粒子へ直接撒く経路を選んだ — 球フィッティングやメディアル軸抽出はしない、それは既存の
  「凍らせる」（`freezeParticlesToBalls`）の仕事のまま。新規実装は二点だけ:
  1. **バイナリSTLパーサ**: 80byte ヘッダ + uint32 三角形数 + 三角形ごと50byte
     （法線12byte・頂点3×12byte・属性2byte、リトルエンディアン）を素朴に読む。この Study 自身の
     書き手はいない（書き出しは cloud-sculpt/meshExport.ts の `encodeBinaryStl` が既に持っている）が、
     同じバイナリレイアウトの読み手として実装した。**ASCII STL は非対応**（T2f-import-stl.md が
     許した二択のうち「正直に断る」を選択 — 作業負荷を抑えるため）。ヘッダが `"solid"` で始まる
     ASCII と、たまたま同じテキストをヘッダに持つバイナリSTLを区別するため、テキストだけでなく
     ファイルサイズが `84 + 三角形数×50` と一致するかで判定する（`looksLikeAsciiStl`）
  2. **内外判定＝ボクセル充填**: 取り込み時にまず正規化 — バウンディングボックスの最長辺を
     MPMドメイン(`DOMAIN_SIZE=8`)の6割へ一様スケールし、x/zをドメイン中心へ、y座標を
     `marginWorld(gridN)+0.05` の上に接地（S1 balls の `liftAboveGround` と同じ「接地余白を取って
     地面の上に置く」流儀）。そのうえで `particlesPerUnitVolume` から求めた格子間隔
     `h = particlesPerUnitVolume^(-1/3)` の点群を走査し、各点から **+X方向へレイを飛ばし三角形との
     交差数の偶奇**で内側を判定する（古典的な point-in-polyhedron のレイキャスト法、出典:
     O'Rourke, *Computational Geometry in C* 2nd ed. §7.5。交差判定自体は
     Möller & Trumbore, "Fast, Minimum Storage Ray-Triangle Intersection", 1997、
     レイ方向を`(1,0,0)`に固定した特化版）。(y,z)の列ごとに三角形の候補（Y/Zバウンディングボックスが
     その列と重なるものだけ）を絞ってからレイキャストするので、列数×三角形数のオーダーだが
     各判定は軽い数値比較のみ（実測は Observation 参照）
  - **粒子数の上限と間引き**: `MAX_MESH_PARTICLES=20000`（README実測の性能表からの外挿 — 3,307粒子
     ~11ms/substep が線形に伸びても20,000粒子で100ms未満に収まる、という根拠）。超えたら
     間引き前の総体積推定（`totalVolume0`）を保ったまま等間隔（stride）で間引き、
     残った粒子の質量を再配分して**総質量を保存**（seeding.ts の球ごとの質量保存と同じ考え方）。
     UIには「間引きました」を明示するアラートを出す（黙って欠けさせない、S1の球数上限の教訓の踏襲）
  - **非水密メッシュへの正直さ**: 偶奇判定は穴・自己交差のあるメッシュで誤判定しうる。
     水密検査やメッシュ修復はこの Study の範囲外（T2f-import-stl.md「やらないこと」）— 種まき欄の
     STL入力の隣に常時ヒントとして注意書きを表示する（`ui.ts`）のみで、検査ロジックは作っていない
  - **履歴**: 新 op を最小で切った（`seedMesh`、`history.ts`）。既存の `seed` は常に
     `seedParticlesFromBalls`（Ball[]からの再サンプリング）で粒子を**再構成**する設計なので、
     ball 由来ではないメッシュ充填をそのまま乗せると再生時の意味が変わってしまう。
     `freeze` が焼き付け結果（Ball[]）を引数に明示的に持つのと同じ流儀で、`seedMesh` も
     **充填後の粒子座標をそのまま引数に持つ**（三角形データは一切履歴に入れない — レシピの肥大を防ぐ、
     T2f-import-stl.md の指示どおり）。質量は座標と一緒に固定値では持たず、`totalVolume0`
     （間引き前の総体積推定）と現在の `params.densityKgM3` から `seed` と同じ考え方で導出する
     （密度パラメータの編集可能性を `seed` と揃えるため）。replay で完全に同じ粒子配置が
     再現されることを実測で確認（Observation 参照）

  WebGPU/WebGLが別々のネイティブGPUコンテキストとして動く可能性が高く、この問題が
  再現しない可能性がある。「実行」ボタン（単発・低頻度の読み戻し）や凍結・エクスポートは

## Hypothesis

- **時間積分そのものが「本物」の一部**: Y6 は構成則（応力の式）を焦点に発注されたが、
  今回観察された最も分かりやすい「入れていない振る舞い」（固体端のバウンド）は、
  構成則そのものよりも「静的な緩和ソルバー」から「動力学の時間積分」への**ソルバーの種類の
  転換**から生まれた。S2b が正しい構成則（Neo-Hookean的な弾性の素描）を持っていたとしても、
  緩和ソルバーである限りバウンドは出せない。本物の原理を持ち込む効果の一部は、
  「正しい式」そのものより「時間発展を追う」という解き方の格に宿るのかもしれない
  — RESEARCH §3「解き方の5系」でいう③数で解く、の中でもさらに細かい違い
  （緩和 vs 積分）として次に整理したい
- **液体端の"S1形式への還流"は雲の記憶を保つ**: 凍結→S1インポートで確認したとおり、
  この Study は「本物の物理で暴れた結果」を安全に S1/S2b の世界（球のリスト）へ戻せる。
  つまりこの Study は「暴れさせる場所」であり、「作品として置く場所」ではない ——
  RESEARCH v3 Y6 の役割分離（計器 vs 形態形成）と同じ形の分離が、Study間の役割分離
  としても機能しているように見える
