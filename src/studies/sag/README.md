# S2b — たわむ (Sag)

*v0.2.0（2026-07-10, T2c）: 柔らかさ1付近を「潰れた固体」から本物の液体の端（濡れ広がる池）に
差し替え、新しい履歴 op `freeze`（たわんだ形を正本に焼き付け、固体に戻す）を追加。
RESEARCH v2 Y5「相の造形」の第一歩。以下、v0.1.0（T2b）の記述は柔らかさ中間〜低の
挙動としてそのまま有効（回帰確認済み）。T2c 固有の設計は Setup の該当節と
Observation の 2026-07-10 の記述を参照。*

## Question

柔らかさのつまみ一本で、雲は自重にどう応えるか。休んでいる形（正本）と、
力の下で実際に起きている形（たわみ、導出物）の**差**を、初めて形の差として見られるか。

*T2c で追加された問い*: 柔らかさ1は「潰れた固体」ではなく本物の液体の端になれるか
（球が滑り落ちて濡れ広がり、一〜二球厚の池に落ち着く）。そして、たわんだ一瞬を
「凍らせて」正本に焼き付ける——導出物が正本に昇格するという、このソフトで初めての
操作——は、道具として自然に振る舞えるか（replay 決定性・こねる操作の継続）。

## Setup

- **場の定義**: S1（`src/studies/cloud-sculpt/`）の `Ball[]`／`FieldParams` をそのまま輸入
  （`field.ts`／`picking.ts` を import、コピーしない）。雲の形の正本は S1・S2 と同じ
- **材料の場の初登場**: `params.ts` の `SagParams = FieldParams & { softness: number }`。
  softness は 0（剛）〜1（柔）、材料は当面一様（T2b-sag.md §1「材料は当面一様」）。
  他のつまみ（count/radiusBase/…）と同じ `setParam` 履歴 op で記録される。
  ただし softness の変更は**育て直し（`grow`）を呼ばない** — 場を作り直すと彫刻した形が消えてしまうため、
  `k` と同様「即時反映のみ、regrow なし」の特別扱い（`main.ts` の `onParamChange`）
- **一番大事な設計の線**: 正本（休み形）= `state.balls`、履歴に記録されるのはこれと手の履歴のみ。
  たわみ（`deformed`）は `deform.ts` の `computeDeform(balls, softness)` — 純関数、毎回同じ入力から同じ出力。
  正本か softness が変わるたび `main.ts` の `recomputeDeform()` で再計算し、メモリ上にキャッシュするだけで
  履歴には一切乗せない
- **たわみの計算**（`deform.ts`、方向性は T2b-sag.md §2 の通り）:
  1. S2 と同じ重なりグラフ（中心間距離 < r₁+r₂）をバネのネットワークとみなす。
     バネの剛性 `k_edge = K_BASE × stiffnessFactor(softness) × overlapArea(r₁,r₂,d)`。
     `overlapArea` は `gravity/physics.ts` から import（コピーしない、この Study のために `export` を追加した）
  2. `stiffnessFactor(softness) = 0.03 + 0.97×(1−softness)` — softness=1 でも完全に 0 にはしない
     （床）。理由: チューニング中、剛性ちょうど 0 だとバネ網が完全に切り離されて画面がバラバラの
     球の山に見え、「柔らかい雲」というより描画の不具合に見えたため、わずかな結束を残す表示上の判断
     （物理的な材料定数ではない）
  3. 各球に自重 `−GRAVITY × ballVolume(r)`（`ballVolume` も physics.ts から import）が下向きにかかる。
     `GRAVITY = 2.2`（スケッチ単位、S1/S2 既定の雲で目視して選んだ）
  4. 地面は `y ≥ r` のハード制約（貫入禁止）。バネは伸びても縮んでも力を返す通常のフックのバネ
     （圧縮方向の反発があるから、鉛直に潰れると横に逃げる — 条件2「裾が広がる」の機構）
  5. 減衰つき半陰解オイラー（"Jacobi/Verlet 的なもの"）を softness>0 のとき固定 240 反復で解く。
     `K_BASE=90`, `DT=1/60`, `DAMPING=0.9`。毎フレームではなく、正本か softness が変わったときだけ実行
     （T2b-sag.md §2「毎フレームでなくてよい」）
  6. **softness ≤ 0 は数値のシミュレーションをせず、完全にバイパスして休み形をそのまま返す**。
     「柔らかさ0でたわみゼロ」（完了条件1）を、剛なバネの極限としてではなく、厳密な等号として保証するため
  7. 「壊れた」判定: 最終状態でどれかのバネが自然長の4倍を超えて伸びる／縮む
     （`BREAK_STRETCH_RATIO=4`）と、その両端の球を `broken: true` とする。NaN/非有限座標になった球も
     `broken: true` にしたうえで休み形の座標にフォールバックし、描画が壊れないようにする
- **二枚の姿**（`renderer.ts`）: 2つの three.js シーン。
  - main: たわんだ球（`deformed.balls`）＋地面。色は S2 の苦しさ
    `computeStrain()`（`gravity/physics.ts` から import）を**たわみ後の配置**で再計算し、
    `broken` な球は苦しさ 1（最大＝赤）に強制上書き
  - ghost: 休み形（`state.balls`）だけをレイマーチした半透明のシルエット。ストレス色ではなく
    中立なパール調グレー（`rgb(0.78,0.82,0.90)`）。フレネル的なリムでアウトラインを強調し、
    たわんだ本体を覆い隠しすぎないようにした。`autoClear=false` で main の後に上書き描画。
    トグル ON/OFF（既定 ON — 差を見るのがこの Study の眼目なので初回から見えるようにした、
    これは指示書に明記のない**仮決め**）
- **こねる = 正本（休み形）への編集、ピッキングはたわんだ表示に対して行う**（T2b-sag.md §3）:
  `raymarchField()`（S1/S2 と同じ、コピーせず import）を `deformed.balls` に対して実行し、
  当たった球の `id` で `state.balls`（正本）の同じ id の球を検索して編集する。
  ドラッグの平面はたわんだ球の現在位置を軸にする（見えている場所を掴む感覚を保つ）が、
  実際に記録される `moveBall` の座標は正本の空間にそのまま書き込む。
  これは「たわんだ絵を掴んで、休み形の値を直接書き換える」という**仮決め**（指示書に厳密な
  座標変換は指定されていない）。新規球の追加も同様、正本へ直接追加する
- **色**: 確定パレット（青 `rgb(0.30,0.55,0.95)` ↔ 赤 `rgb(0.95,0.25,0.20)`）を S2 の
  シェーダからそのまま複製（新色は発明していない）
- **常設バナー**: 「粗い近似: バネの素描。弾性論ではない。実物の保証はしない。（S3 で実物と校正予定）」
  （T2b-sag.md §4 の文言そのまま）
- **技術選定**: S1/S2 と同一（vite + three.js + 素の TypeScript）。理由も同じ
- **入り口**: `sag.html`（`vite.config.ts` の `build.rollupOptions.input` に追加）。
  S1・S2 のパネルにも「S2b たわむ →」のリンクを追加、S2b から S2 へは「← S2 重力を入れる」

### T2c（v0.2.0）: 液体の端

`deform.ts` の `computeDeform(balls, softness)` は softness=0 の厳密バイパスはそのまま、
0を超えると常に **2つの独立した解を softness でクロスフェード**する:

- **`solveSpring`（T2b、無変更）**: 休み形の重なりグラフを永続的なバネ網とみなす、既存のまま。
  softness が `LIQUID_BLEND_START`(=0.65) 以下ではこの結果を**単独でそのまま返す**
  （液体の解を計算すらしない）ので、柔らかさ中間（例0.4）は T2b とビット単位で同一
  （回帰確認済み、下記 Observation）
- **`solveLiquid`（新規）**: 「接続の記憶を持たない」——エッジを固定せず、毎反復
  **現在位置**からペア力を再構築する（O(n²)、球数はスケッチ規模なので軽い）。
  各ペアは重なり目標距離 `LIQUID_REST_RATIO × (r_i+r_j)`（=0.6×）に向かう:
  それより近ければ押し返し（`LIQUID_K_REPEL=80`）、遠ければ引き合う（`LIQUID_K_COHESION=5`）、
  ただし `LIQUID_COHESION_REACH=1.05×(r_i+r_j)` を超えると力ゼロ（接続なし）。
  重力は `LIQUID_GRAVITY=3.5`（バネ解の 2.2 より強い——RESEARCH v2 Y5「液体の端=形は重力のもの」の
  実装的反映であり、かつ固定反復数で確実に潰すために実務上も必要だった）。
  地面制約は **ball ごとの半径の 35%（`LIQUID_GROUND_EMBED_RATIO`）だけ「y=r」より深く**沈める
  （バネ解の厳密な `y=r` とは異なる——理由は後述）。
  反復は**二段階の減衰スケジュール**（`LIQUID_PHASE1_ITERATIONS=300` @ damping 0.98 の
  「エネルギッシュな」段階、続いて `LIQUID_PHASE2_ITERATIONS=500` @ damping 0.8 の
  「収束」段階、計 800 反復）——単一の減衰では「山のまま少し潰れる」止まりで、
  低減衰の探索段階がないと重なった球が横へ逃げる前に力が死んでしまうことが
  チューニング中にわかった（下記の失敗した設計を参照）
- **クロスフェード**: `smoothstep(LIQUID_BLEND_START, 1, softness)` を重みとして、
  2つの解の**座標のみ**を線形補間（`x/y/z`、`id`/`r` は元のまま）。softness=1 で純粋な液体解になる。
  「壊れた」フラグは重み<1の間はバネ解のものをそのまま使い、重み=1（softness=1 ちょうど）では
  常に false（液体解には破断の概念がない——後述）
- **なぜ地面に少し埋めるか（`LIQUID_GROUND_EMBED_RATIO`）**: 完了条件2「池はほぼ青」の
  ために不可欠だった。`gravity/physics.ts` の `computeStrain` は接地する球の負担を
  「接地面積」で割るが、球と平面の理想的な接触は**幾何学的に面積ゼロの一点**——
  バネ解と同じ厳密な `y=r`（貫入禁止のみ、埋め込みなし）のままだと、池のほぼ全球が
  接地根（root）になり、どの球も接触面積ゼロ＝最大の苦しさ（赤）になってしまう
  （最初の実装でこれを踏み、池が真っ赤になった）。「ベタッと」なる液体は現実にも
  接地面が実際にある——それを 0.35×r の埋め込みとして与えた。`gravity/physics.ts`
  自体は変更していない（S1/S2 の変更はしないこと、指示書の「やらないこと」）
- **試して捨てた設計**（README に理由つきで残す、AGENTS §7）:
  1. 重なり目標を「ちょうど接触」(比率1.0) にする → 接触面積がほぼゼロになり
     池が赤一色になった（上記の埋め込みで解決する前の症状そのもの）
  2. 凝集の届く範囲を広く（3〜4倍）＋強く → 元のクラスタ全体を一つの塊として
     引き留めてしまい、重力で潰れても横にほとんど広がらなかった（spread が
     rest とほぼ同じ 2.2 のまま）
  3. 単一の減衰係数（バネ解と同じ流儀）→ 高い減衰では動けず、低い減衰では
     いつまでも収束しなかった。二段階（エネルギッシュ→収束）に分けて解決
  4. 届く範囲を狭く（1.0付近）＋凝集を弱く だけにすると、初期のエネルギッシュな段階で
     数球（デフォルトの雲で12球中0〜2球程度、他のシード/球数でも概ね同程度）が
     クラスタから完全に外れ、孤立した水滴として着地することがある——実用上は
     「一〜二球厚の池」の要件をほぼ満たしつつ、稀にこの飛沫が生じる。これは
     完全解決を狙わず、**点接触の特異点と同様に指示書が認めている例外**として記録する
     （下記 Observation の実測値を参照）
- **液体解に「壊れた」の概念がない理由**: `solveSpring` の破断判定（自然長の4倍を超える
  伸縮）はバネの自然長という概念に依存するが、`solveLiquid` にはそもそも固定の自然長が
  ない（毎反復再構築されるため）。液体が「壊れる」とすれば、それは孤立した水滴や
  一点接触の特異点として現れる——上の「試して捨てた設計」④参照

### 新しい履歴 op: `freeze`（T2c）

- 引数なし。`history.ts` の `applyEntry` が `computeDeform(state.balls, state.params.softness)`
  を呼び、その結果を `state.balls` に焼き付け（`id`/`x`/`y`/`z`/`r` をそのままコピー）、
  `state.params.softness` を 0 に戻す
- **replay 決定性**: `computeDeform` は純関数（正本と softness のみに依存、反復数固定）であり、
  `freeze` が呼ばれる時点の `state` は履歴の再生によって常に同じ値に決定的に再構築されるため、
  同じ履歴を再生すれば `freeze` は常に同じ座標を焼き付ける。**たわみ座標そのものを履歴に
  保存するわけではない**——「何をベイクするかの意図（レシピの一手）」だけを記録する点は
  他の全 op と同じ設計（正本＝場＋操作の履歴、README冒頭 T2b の記述のまま）
- **視覚的な証拠**: freeze 直後は softness=0 なので `computeDeform` は厳密バイパスに入り、
  ゴースト（休み形）と本体（たわみ）が数値的に完全一致する——「凍った」ことの検算になる
- **freeze 後もこねる操作は普通に続く**: `id` を保ったまま焼き付けるので、選択中の球の選択状態も
  維持され（`main.ts` の `freezeNow()` は選択をクリアしない、意図的な仮決め）、追加・移動・
  半径変更・再度柔らかくして再びたわませる…がすべてそのまま履歴に積み重なる
- UI: 「材料の場」節、柔らかさスライダーのすぐ下に「凍らせる (Freeze)」ボタン
- **つまみのラベルは変更していない**（指示書指示通り、「相」への改名は T2d 判断）
- **バナー**: 「液体は表面張力の素描。流体力学ではない。」を既存の一文に追記

     softness を 0.5, 1.0 と上げると、既定の雲（count=12, radiusBase=0.7）の全体高さが
     約 2.998 → 1.930（softness=0.5）→ 1.740（softness=1.0）と連続的に潰れていった
  2. 同じ比較で、球の中心から鉛直軸までの水平距離（`hypot(x,z)`）の最大値が
     2.212 → 2.392 → 2.406 と広がった。個々の球でも一部（例: 0.50→0.71→more、1.21→1.54）が
     明確に外へ逃げているのを確認 — 潰れが横に逃げる「裾が広がる」挙動が見えた
     （全球が一様に外へ広がるわけではなく、内側に寄る球も一部あった。バネ網の非一様な
     応答として妥当だが、「裾が広がる」の見え方は場によって強弱があると思われる）
  3. スクリーンショットで確認: softness=0 では休み形とたわみ形が完全一致するためゴーストは
     見えず（正しい振る舞い）、softness=0.4 では休み形の淡い水色のシルエットが、潰れた赤い本体の
     上に明確にはみ出して見えた（差が一目でわかる）
  4. 合成の pointer イベント（`pointerdown`/`pointermove`/`pointerup` を直接 dispatch）で:
     空クリックで新規球を追加（履歴に `addBall`）、既存球をクリックで選択（苦しさも表示）、
     選択中の球をドラッグすると `moveBall` が記録され `getBalls()`（正本）の座標が実際に変わることを確認。
     半径スライダーでも `setBallRadius` が記録され、正本の半径が変わった
  5. `exportJson()` → 空の履歴を `importJson()` → 元の JSON を再度 `importJson()` で、
     `getBalls()` / `getDeformed()` / `getParams()` の JSON 文字列がすべて完全一致
     （`softness` を含む setParam エントリは履歴に残り、たわみ座標は一切含まれていないことを
     `exportJson()` の中身を直接検査して確認 — ops は `grow/setParam/addBall/moveBall/setBallRadius` のみ）
  6. バナー文言が画面左上に常設表示されているのを確認（テキストは指示書の文言そのまま）
  - **壊れた球の検出**も合成データで確認: 巨大な球を極小の球1つだけで支える病的な構成
    （半径0.15の支え球の上に半径1.5の球）を softness=1 で解かせると、両球とも `broken: true` になり、
    座標は有限値のまま（NaN にならず）地面に落ち着いた
  - **応答速度（実測）**: softness スライダーを 0.2/0.5/0.8/1.0/0.0 と動かして、`setParam` 記録
    → `recomputeDeform()`（240反復の緩和）→ `render()` 完了までの同期実行時間を計測。
    いずれも **1〜4ms**（`getLastSoftnessResponseMs()` の値: 3.8, 1.1, 0.9, 1.0, 0.0 ms）。
    240反復×球数12前後というスケールでは、毎フレーム再計算しなくても体感は一瞬だった

    （S1/S2 の記録と同じ注記: headless verification と実機は異なりうる）

## Hypothesis

- 「柔らかさ」ひとつのつまみでも、向き（柔らかいほど潰れる・裾が出る）は直感と合う。
  ただし現在の近似は球ごとの支持経路のトポロジーに敏感（S2 の Hypothesis と同根の限界）で、
  同じ softness でも彫刻の仕方次第でどの球が「壊れた」になるかは不連続に変わりうる
  （今回は明示的な発散判定を入れたことで、その不連続さを「壊れた＝赤」として正直に見せる方に倒した）
- 剛性フロア `0.03`（softness=1 でも完全に0にしない）は表示の安定のための妥協であり、
  「本当に無限に柔らかい材料」を模したい場合はここが効いてくる。材料が球ごとに異なる段（後の段）
  になったとき、この定数の意味を作者と相談したい

- **（T2c）液体らしさは「重なり目標＋二段階減衰」から出た、こちらの直感的想定とは違う経路だった**:
  当初は「近い球は引き合い、重なりすぎは押し返す」というシンプルな一段階の力場だけで
  自然に濡れ広がると予想したが、実際に効いたのは (a) 重なりの目標距離を「ちょうど接触」
  ではなく実際の場の典型的な重なり深さ（0.6倍）に置く判断（S2/S1 の場そのものの性質から
  逆算する必要があった）と、(b) 減衰を単一値でなく二段階にする判断（最初のエネルギッシュな
  段階がないと、重なった球が地面に落ちる過程で横へ逃げる前に力が死ぬ）。物理を直接
  「表面張力」から発想するより、**この場の既存の重なり統計に合わせる**ほうが早く安定した——
  Y5「相の造形」は原理の見た目の名前（表面張力）よりも、この場が持つ数値的な癖
  （重なり深さ・接地面積の扱い）との相性を先に解く方が近道なのかもしれない
- **飛沫の発生は「してはいけないバグ」というより「液体らしさの兆候」かもしれない**:
  凝集の届く範囲を狭くするほど、少数の球が孤立した水滴として飛び散る（Observation 参照）。
  これを完全に抑えると（届く範囲を広げる）今度は池自体が広がらなくなるという裏返しの
  トレードオフがあり、両立しない。RESEARCH v2 Y5 が「しぶきの瞬間」を凍らせる対象として
  名指ししていることを踏まえると、この飛沫は欠陥ではなく、`freeze` で捕まえるべき対象の
  萌芽ではないか——次の Study 訪問で作者と相談したい
