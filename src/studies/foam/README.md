# S-foam — 泡のセル (Foam Cells)

## Question

同じ雲(球のリスト)を、セルに分解して見るとどうなるか。
穴を第一級の造形要素にしたとき、体積のある殻から中身のない糸(Plateau 境界)まで、
一本のつまみで連続に渡れるか。渡れないとしたら、どこで千切れるか。

## Setup

- **場の定義(正本は変えない)**: 雲 = 球のリスト(中心・半径)。field.ts を cloud-sculpt からそのまま
  import して共有している(コピーしていない)。foam は S1 と同じ球のリストの上に立つ**別のレンズ**
  であり、球のリスト自体を書き換える手段はこの Study にはない(セルの個別編集はやらないこと、
  T7-foam-cells.md の指示どおり)
- **セル分解(選定と理由)**: 教科書的な power distance `|p-c|² - r²` ではなく、既に field.ts にある
  `ballSdf(p) = |p-c| - r` を各球の「距離」として使う。理由: 追加のチューニング定数なしに
  半径に追従するセルサイズが手に入り、かつ雲の輪郭(fieldSdf)・ピッキング・メッシュ化と単位が揃う。
  各点で全球の ballSdf を求め、最小 d1・2番目 d2・3番目 d3 を(ソートでなく3本の走行最小値で)追跡する:
  - `cellWall = d2 - d1` — 0 がちょうど2セルの境界(Voronoi 壁)
  - `cellEdge = d3 - d1` — 0 がちょうど3セルが会う Plateau 境界
- **泡の SDF**(`cell.ts` の `foamSdf`、GLSL 版は `shaders.ts` の `map()` に厳密に対応させてある):
  1. 雲の面 `surf = fieldSdf(balls, k, p)`(S1 と同じ smooth-min)
  2. どちらの膜に属するか: `cellWall < |surf|` なら内部の壁、そうでなければ外殻
  3. 膜の「縁からの遠さ」: 壁なら `cellEdge`、外殻なら `cellWall` 自身(外殻上でセル境界に
     近づくことが、外殻にとっての Plateau 境界にあたる)
  4. 開口幅 `openWidth = lerp(cloudScale·0.9, thickness·0.6, opening)` を `thickness·0.5` で
     床止め(1 付近でも Plateau 境界の糸だけは残るように)
  5. `keep = 1 - smoothstep(openWidth·0.65, openWidth, edgeDist)` → 縁に近いほど残す
  6. `membraneDist = smoothMin(cellWall, |surf|, k·0.3)`、`shellCore = membraneDist - thickness`
  7. `foamSdf = smoothMax(shellCore + (1-keep)·6, surf - thickness, k·0.3)`
     (雲の面から `thickness` 以上外に材料が漏れないようキャップ)
  - `k`(既存の S1 つまみ)は壁と外殻の合成、および開口キャップの丸めに使う
    (T7 指示書「smooth-min の k は泡でも生きる」)
  - **既知の限界**: これは真の Euclid 距離場ではない(特にホールの近く)。マーチング四面体
    (符号だけ見る)には十分だが、レイマーチのスフィアトレースはオーバーシュートしうるので
    ステップを 0.6 倍に減衰させている(下記の応答速度参照)
  - **既知の限界その2**: `cellEdge`/`cellWall` は各点で独立に最近傍3球を求める素朴な規則で、
    大域的な Voronoi 隣接グラフの整合性を持たない。3球の「顔ぶれ」が空間内で切り替わる境目で
    Plateau 境界の帯が局所的に途切れることがある → 下記「水密の実測」で厚みを上げると
    繋がりやすくなることを確認(Next 参照)
- **表示**: レイマーチング(`shaders.ts`)。S1 と同じフルスクリーンクアッド構成。最近傍3中心の
  逐次探索をシェーダ内で行う(3D テクスチャへの焼き込みは不要だった — 球数上限256のループで足りた)
- **こねる手はない**: T7 の「やらないこと」どおり、球のクリック追加/選択/移動はこの Study では
  実装していない。手はつまみ(開口・厚み・S1 と同じ球生成つまみ)と grow/reroll のみ
- **出口(3Dデータ)**: `cloud-sculpt/meshExport.ts` の marching tetrahedra 機構をコピーせず再利用。
  `buildCloudMesh` の内部から `buildMeshFromField(bounds, sdf, options)` を切り出し、
  `computeSamplingBounds` を export した(S1 側の `buildCloudMesh` の呼び出し・挙動は不変 —
  下記「無退行の実測」で同一出力を確認済み)。foam 側は `buildFoamMesh` がこの汎用関数に
  `foamSdf` を差し込んで呼ぶだけ
- **正本と履歴**: foam は自分専用の `{t, op, args}` 履歴を持つ(studyId "foam")。
  op = grow / setFieldParam / setFoamParam / loadBalls / clear。S1 のレシピは「読み込み専用」で
  対応: S1 の `parseRecipe`/`replay`(import のみ、変更なし)で球のリストへ変換し、
  foam 側は `loadBalls` という1エントリとして自分の履歴に記録する(以後は foam 独自の履歴だけで
  再現できる)
- **技術選定**: vite + three.js + 素の TypeScript。S1 と同じ構成(フレームワークなし)

### 応答速度(実測 — isolated Chrome headless + software WebGL, port 5185)

- 開口スライダー変更 → 状態更新まで: 約 `0.1 ms`(即時反映、`k` と同じくその場で再生成なし)
- 育て直す(Grow)ボタンの実座標クリック → 履歴1件追加: 確認済み(ヒットテスト一致)
- レイマーチ fps: headless では `~2 fps`。S1(素の smooth-min のみ)の `~1 fps` 台と同オーダーだが、
  foam の `map()` は最近傍3球の走行追跡 + 220 回反復(S1 は128回)を毎ステップ行うため重い。
  本番デスクトップ実機では別途再計測が必要(S1 README と同じ注記)
- メッシュ検査の所要時間(既定の12球の雲、開口=1・厚み=0.035、最長辺80mm):

  | 解像度 | 三角形数 | 所要時間 | 水密 |
  |---|---|---|---|
  | 32 | 336 | 44 ms | OK |
  | 64 | 2,708 | 166 ms | NG(非多様体辺 4) |
  | 96 | 8,088 | 536 ms | OK |
  | 128 | 19,868 | 1,256 ms | NG(非多様体辺 12) |
  | 160 | 37,320 | 2,397 ms | OK |
  | 192 | 63,564 | 4,100 ms | NG |
  | 256 | 136,172 | 12,925 ms | NG |

  解像度を上げても水密性が単調に改善しない(NG/OK が交互)。原因は上記「既知の限界その2」の
  Plateau 境界の局所的な途切れ — 格子とごく細い壁が特定の位置関係になると縮退三角形
  (非多様体辺)が生じる。三角形数は全解像度で少数(数個〜十数個の辺)なので実害は局所的

### 水密の実測(完了条件4)

- **開口0(閉じた殻)**、既定12球、解像度128、最長辺80mm: **373,512 triangles**、
  80.0 × 71.2 × 76.2 mm、**水密 OK**(openEdges=0, nonManifoldEdges=0)
- **開口1(糸のみ)**、厚み既定0.035、解像度96: 8,088 triangles、水密 OK だが
  **連結成分170個**(頂点の37.6%しか最大成分に属さない)— 見た目は「網」ではなく「粉々」に近い。
  上記「既知の限界その2」のとおり、細い糸だと局所的な途切れが致命的になる
- **厚みを上げると繋がる**(同じ12球・開口1・解像度96で厚みを掃引):

  | 厚み | 三角形数 | 水密 | 連結成分数 | 最大成分の頂点比率 |
  |---|---|---|---|---|
  | 0.035(既定) | 8,088相当※ | OK | 170 | 37.6% |
  | 0.05 | 16,940 | OK | 292 | 6.6% |
  | 0.07 | 32,040 | OK | 282 | 6.9% |
  | 0.09 | 48,540 | OK | 170 | 37.6% |
  | 0.11 | 65,144 | NG(非多様体) | 79 | 70.6% |
  | 0.15 | 100,204 | OK | 21 | **98.6%** |

  ※連結成分表は解像度96・厚み0.035再計測時点の値(三角形数は乱数状態により行間で若干異なるが
  傾向は一致)。**この雲(12球, r=0.7, spread=0.5, k=0.6)では、開口1で「糸の網」として
  実用的に繋がるには厚み ≳0.15 が必要**、というのが正直な実測。既定値0.035は「見た目に細く
  美しい」が「網としては千切れがち」— 千切れたらそのまま NG と表示する(千切れを隠さない)方針を守った
- **千切れの表示**: 「メッシュを検査」ボタンは常に実測の三角形数・mm寸法・水密可否
  (openEdges/nonManifoldEdges 内訳つき)を表示する。嘘の「水密です」は出さない

## Hypothesis

- ballSdf ベースの最近傍3球という「各点で独立」な規則は、真の Voronoi/Delaunay 隣接グラフの
  大域的整合性を持たないため、Plateau 境界が細いときに局所的に途切れやすい。
  厚みで橋渡しできる範囲では実用になるが、糸を本当に細くしたい(意匠として)なら
  隣接関係を明示的なグラフとして先に確定させる設計が要る
- 開口という一本のつまみで「どのセルも同時に」体積→殻→糸へ渡る操作は、
  RESEARCH Y7 の「穴が第一級要素になる」を最小の形で満たせた。ただし糸の**トポロジーの
  信頼性**(繋がっているかどうか)は、殻の水密性(完全に閉じているか)よりずっと壊れやすい
  性質だとわかった — 「余白の実体化」は形になった瞬間から脆さと同居する
