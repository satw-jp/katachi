# S-skin — 表面に詰める (Surface Patch Packing, T10 / T11 v0.2 リングの皮)

## Question

RESEARCH.md v5「Y7 表面版」（作者の言葉、2026-07-11、虚のパッキング（T9/S-pack）の姉妹）:

> 「ある形態の**表面に**ランダムな閉じた平面形状をパッキングする」
> 「**平面形状が実体で形態が虚になることもあればその逆もある**」

T9（S-pack）が体積の内部を虚で詰めて骨組みを残したのに対し、この Study は表面を不定形の
閉パッチで詰める。新要素は**実と虚の反転可能性（地と図の裏返し）**:

- 同じパッキング結果から、**プレートが実**（パッチだけが物体になり、形態そのものは印刷され
  ない — バラバラの部品）と、**形態が実**（殻に窓が開く — 殻は繋がったまま）の、両方が出るか
- その反転を、パッキングをやり直さずに**ワンタッチで往復**できるか
- 「不定形の閉じた平面形状」を、真円にせずに、簡単な仕組み（表面上の副点群の smooth-min）
  だけで作れるか
- 目地 g（パッチ間に残る肉/隙間の最小幅）という一つのつまみが、両方のモードで正直に
  機能するか（窓版では「骨の太さ」、プレート版では「部品どうしが融合するかどうかの境目」）

### v0.2 (T11「リングの皮」) の問い（作者発注 2026-07-13）

> 「今は実体のときにコインを敷き詰める感じだけど、**リングを敷き詰めたときはリングによって
> 総体の形状ができるのが見たい**」

コインの点在は分離した部品だった。リングには穴があるので、隣同士が**絡み合える** —
接着なしで布として繋がった皮（鎖帷子）になり得るか。具体的には:

- パッチ形状をコイン／平リング（内孔率つまみ、窓モードで O 字窓）／立体リング（S-rings の
  語彙を輸入したトーラス）で切り替えられるか。既存のコインは無変更か
- パッキング間隔（目地 g）に**負側**（重なり許容）を持たせると、立体リング同士の絡みが
  貪欲配置の偶然として生まれるか
- S-rings の Gauss linking number を流用した**絡み計器**（絡んだペア数・連結成分数）で、
  「布になったか点在か」が数字で読めるか
- **立体リングだけでホストの総体形状が読める**（ホスト表示なしでも形が立ち上がる）か

## Setup

`src/studies/skin/` に自己完結。`skin.html` から起動。

- **ホスト**: S1 と全く同じ場の定義。`cloud-sculpt/field.ts` の `Ball`・`FieldParams`・
  `fieldSdf`・`growBalls` をそのまま import（コピーしない）。既定は S1 と同じ
  `DEFAULT_FIELD_PARAMS` での grow。「S1 レシピを読み込む」でホストを輸入できる
  （T9 の `loadHostFromS1Recipe` と同じ設計 — S1 自身の `parseRecipe`/`replay` を使って
  再生し、結果の球リストを1エントリとして記録する）
- **殻**（`field.ts` の `shellSdf`）: `|hostSdf(p)| - 厚み/2`。負なら殻の内部。厚みはつまみ
  で、プレート版の板厚も兼ねる（T10 §1 の指示どおり）
- **パッチ**（`field.ts` の `Patch` / `patchesSdf`）: 表面上のアンカー点 + 3〜8個の副点。
  すべて **S1 の球と同じ smooth-min の式**（`cloud-sculpt/field.ts` の `smoothMin`・
  `ballSdf` をそのまま流用）で結合される — 構造的には「もう一つの Ball[]」でしかなく、
  距離場の数式は何も新しく発明していない（新しいのは**置き方**だけ:
  点が開いた空間ではなく曲面に沿って並ぶ）
  - **輪郭の式**（README で明示すべき箇所）: アンカー点は
    `field.ts` の `projectToSurface`（SDF 勾配方向への Newton 法反復、`x -= n * hostSdf(x)`
    を最大24回）でホストの零等値面（`hostSdf=0`）に正確に落とす。副点はアンカーの
    接平面（`tangentBasis` — 法線に直交する二本の基底ベクトル）内でランダムな角度・距離に
    散らし、それぞれ再びホスト表面へ射影する（6回までの簡易版 Newton 法）。全点を
    `roundK` で smooth-min した distance field がパッチの輪郭であり、真円にはならない
    （副点の数と散らばりの強さ = 「形の不揃い」つまみが直接効く）
  - 複数パッチは**一枚の flat union**（全パッチの全点をまとめて一括 smooth-min）。T9 が
    虚どうしの union と host−void の減算に一本の `roundK` を再利用したのと同じ仮決めを、
    ここでも踏襲した（パッチ内の副点の融合と、殻とのブーリアン演算に同じ `roundK` を使う）
- **合成（この Study の眼目、`field.ts` の `compositeSdf`）**:
  - **プレートが実**: `opSmoothIntersection(殻, パッチ群, roundK)` = 殻 ∩ パッチ群
  - **形態が実（窓）**: `opSmoothSubtraction(パッチ群, 殻, roundK)` = 殻 − パッチ群
  - どちらも Inigo Quilez の smooth boolean（https://iquilezles.org/articles/distfunctions/ ）。
    T9 の `opSmoothSubtraction` と同じ形の式を、この Study のためにもう一つ
    `opSmoothIntersection` として自前で実装した（skin/field.ts が自己完結するよう、pack
    からは import せず同じ式を独立に書いた — pack が foam から独立していたのと同じ判断）
  - モード切替は**履歴の一操作** (`setMode`)。パッキング自体には触れないが、export→import
    で完全再現するために記録する
- **詰める手**（`field.ts` の `packPatchesGreedy`、T9 の表面制約版）:
  1. ホストの bounding box から一様乱数で点をサンプル
  2. ホスト外なら棄却
  3. `projectToSurface` でホスト表面へ射影（失敗したら棄却）
  4. アンカーの置ける最大半径 = `min(パッチ大きさ上限, 他パッチとの最短距離 − 目地g)`
  5. `パッチ大きさ下限` を下回れば棄却
  6. 採用したら、接平面内に副点を散らし、各副点も**独立に**他パッチとの目地を守る半径へ
     クリップ（狭すぎれば MIN_SUBPOINT_R 未満として、その副点自体を省く — 見えない
     豆粒として残すより、素直に落とす）
  - 連続棄却が `FAIL_LIMIT` 回続いたら「置けなくなった」と判定して早期終了（T9 と同じ規約）
  - 履歴 op `packPatches` は**結果（アンカー・副点・サイズを含む Patch[] 全体）を引数に持つ**
    （T9 の `packVoids`・mpm の `freeze` と同じ設計 — replay は乱数のウォークも表面射影の
    Newton 法も再実行しない）
  - 手動追加（「パッチを手で追加」ボタン→ホスト表面クリック）は、目地の制約を受けない
    簡易な3点スプレー（アンカー+副点2つ）。T9 の手動虚追加と同じ「意図的な範囲決定」
    （目地を守った完全なパッキングロジックを毎クリック走らせるのではなく、素朴な形を置く）
- **計器**（`field.ts` の `estimateMortar`・`estimateCoverage`・`estimatePatchComponents`）:
  - **最薄の目地／プレート最小間隔**: 全パッチ間の全点ペアの `距離-r1-r2` の最小値
    （T9 の `estimateThinnestWall` と同じ「厳密でない安価な代理指標」の方針）。**一つの数値が
    二通りに読める**: 窓モードでは「窓と窓の間に残る骨の最小太さ」、プレートモードでは
    「二枚のプレートがどれだけ接触に近づいたか」（接触すれば意図に反して一つの部品に
    融合してしまう境目）
  - **表面被覆率（粗い推定）**（`estimateCoverage`）: 二段重ねの近似。①殻の帯
    （`|hostSdf| < 厚み/2`）内に落ちたサンプル点の割合を「表面上にある」の代理とし
    （体積のモンテカルロで面積を近似 — 曲面上の真の面積積分ではない）、②そのうち
    パッチ内（`patchesSdf < 0`）に入った割合を被覆率とする。両方の近似を隠さず明記する
    （AGENTS §6「正直な計算」）
  - **連結成分数（パッチ隣接の推定・プレート版）**（`estimatePatchComponents`）: パッチ
    どうしの点ペアが `roundK*0.5` 以内に近づいたら「融合する」とみなす union-find の
    **速報値**。プレートモード向け（いくつのパッチが融合して何個の部品になるか）で、
    **窓モードの殻の連結性については何も語らない**（殻がいくつに分かれるかは
    ホストの位相とパッチの配置に依存し、パッチどうしの隣接だけでは決まらない）と
    README とコード両方に明記した
  - **完了条件3が求める「N 個の分離した部品」の正本**は、上記の速報値ではなく
    `meshExport.ts` の `countConnectedComponents`（実際に生成した三角形メッシュの
    共有頂点に対する union-find。`cloud-sculpt/meshExport.ts` の `inspectWatertight` と
    同じ頂点量子化規約を使う）。ライブ計器はパッキング直後の速報、メッシュ検査後の
    数字が実測値、という二段構えにした
- **出口**（`meshExport.ts` の `buildSkinMesh`）: `cloud-sculpt/meshExport.ts` の
  `buildMeshFromField`・`computeSamplingBounds`・`encodeObj`・`encodeBinaryStl`・
  `meshSummary` を再利用。サンプリング境界はホストの bounds を殻の半厚み分だけ
  外側にパディングしたもの（殻は `|hostSdf| < 厚み/2` なので、ホストの素の球envelope
  より外に厚み/2だけはみ出しうる）。レシピは独自形式（`studyId: "skin"`）— T9 と同様、
  パッチは S1 やパックの正本には表現できないため
- **技術選定**: vite + three.js + 素の TypeScript。既存 Study と同水準

### v0.2（T11）: パッチ形状の切替

- **`Patch.shape: "coin" | "flatRing" | "ring3d"`**（`field.ts`）。パッチは相変わらず
  「もう一つの Ball[]」（file header の原則）のまま — 形状ごとに変わるのは点の**置き方**
  だけで、距離場の式（`patchesSdf`・`smoothMin`）は一切増えていない
  - **コイン**: T10 のまま無変更（`buildCoinPoints`、旧 `packPatchesGreedy` の本体をそのまま
    切り出した関数）
  - **平リング**（`buildFlatRingPoints`）: アンカーの接平面内に、内孔率 `flatRingHoleRatio`
    （0..0.95）から決まる半径の円周上に `ringNodeCount` 個のノードを並べ、それぞれ表面へ
    再射影する。式（仮決め、README に理由つきで残す方針どおり）:
    `majorR = anchorR * holeRatio`、`nodeR = anchorR * (1-holeRatio) * 0.9`。
    外周は holeRatio に関わらずおよそ `anchorR` に一致し（`majorR+nodeR ≈ anchorR`）、
    内側の穴（`majorR-nodeR`）は holeRatio が概ね 0.47 を超えたところで初めて正になる
    （それ未満はノードが中心で重なりコインと同じ見え方になる）
  - **立体リング**（`buildRing3dPoints`）: S-rings の `generateRingBalls`・`rotatePoint`
    を import（コピーせず共有 — T11 の「最大限共有」指示）。中心 = アンカー +
    法線×管太さ、軸 = 法線、として `RingRecipe` を作ると、生成されるトーラスは
    アンカーを含む円周ぴったりでホスト表面（の接平面近似）に接する（トーラスの中心を
    管半径だけ持ち上げると、最近接点の高さがちょうど0になる、という初等的な接線条件）。
    「法線まわりの回転はランダム」は `generateRingBalls` 自体には位相パラメータが
    無いため、生成後に `rotatePoint` で軸まわりランダム角だけ回して満たした
  - **`generateShapePoints`** が上記3つの分岐点。貪欲パッカー（`packPatchesGreedy`）と
    手動追加（`main.ts` の `handleClick`）の両方から同じ関数を呼ぶ
- **重なり許容**（T11 §2）: `SkinParams.gap` は既存のまま「クリアランス − gap」の式を
  一切変えていない。UI スライダーの範囲を `-0.3..0.3` に広げただけ（`ui.ts`）—
  負の gap は「他パッチとの最短距離 + |gap|」を許容半径として使うことになるので、
  立体リングの管が隣のリングの穴を貫通できるだけの重なりが自然に生まれる
- **プレートモードの形状分岐**（`field.ts` の `compositeSdf`、`shaders.ts` の GLSL 版と
  CPU/GPU 両方に同じ分岐を実装）: コイン・平リングは従来どおり殻と交差（`shell∩patches`）
  してホストに沿った薄板になるが、立体リングは殻と交差**しない**（生の `patchesSdf` を
  そのまま使う）。理由: リングは表面に一周だけ接する3D物体で、殻の薄い帯に交差させると
  ほとんど削られてスライバーになってしまう。この分岐のおかげで「立体リングだけの
  プレートモード」は自動的に「ホストが実質不可視の状態」になり、完了条件3の
  「ホスト表示 off でも形が立ち上がる」が**専用の表示トグルを作らずに**満たされる
  （プレートモード＝立体リングにとってのホスト非表示、という読み替え）
  - GLSL 側は `uPatchData[i].y`（既存の owner インデックス用 float）に
    `ownerIndex + (isRing3d ? 0.5 : 0)` という端数オフセットで形状フラグを畳み込み、
    4本目の uniform 配列を増やさずに済ませた（この Study は T10 の時点で一度
    uniform 予算超過を踏んでおり、配列を増やす選択は避けた）
- **絡み計器**（新規ファイル `linking.ts`）: S-rings の `linking.ts` の
  `gaussLinkingNumber`（離散中点則の Gauss 連結積分、式の出典は S-rings README 参照）を
  そのまま import。立体リングの `points` 配列はノード生成順そのままの閉じた折れ線なので、
  アダプタなしで渡せる。隣接ペア（点ペアの最短クリアランスがサイズの3倍以内、仮決め
  ヒューリスティック）だけ Gauss 和を計算し、丸めた絡み数が非ゼロなら union-find で
  連結成分にまとめる。「絡んだペア数 / 隣接ペア数」と連結成分数を計器パネルに表示
  - **深いめり込み警告**（`findDeepPatchOverlaps`）: S-rings の `findDeepOverlaps` と
    同じ 0.55 のしきい値・同じ「材料的根拠なしの第一稿」という位置づけを踏襲。
    リングに限らず任意の2パッチ間で判定する
- **メッシュのサンプリング境界**（`meshExport.ts`）: 従来の「ホスト bounds を厚み/2だけ
  パディング」という式は、立体リングが殻の帯を大きく超えて張り出すケースを取りこぼす
  ため、パッチの全点の実際の座標＋半径から直接 bounds を拡張する方式に置き換えた
  （厳密・データ由来で、コインのみの場合は従来の結果を包含する上位互換）
- **UI の正直な上限表示**（`main.ts` の `updateSelectionLabel`）: 立体リングは1パッチ
  あたりの点数（節数分）がコインの副点より多く、`PATCH_MAX_POINTS`（GLSL uniform
  予算の実質的な天井、256）に画面表示が届きやすい。総点数がこの上限を超えたら
  「画面は点群の先頭256個のみ表示（全◯点はSTL/検査には含まれる）」と明記する

### v0.3（T12「生きた表示」）: 選択ハイライトの修理とビーズ近似表示

作者報告2件（2026-07-13）:「平リング、立体リングが選択しても青くならない。でも挙動としては
できているっぽい」／「レイマーチにこだわらなくてもよいから、もう少しインタラクティブに確認
できないだろうか、メッシュ確認は重い」

- **選択ハイライトの真因**（`main.ts`/`shaders.ts`/`renderer.ts` を精査・実機検証）: 疑い筋として
  指示書にあった「`uPatchData` の owner に形状フラグ（ring3d の `+0.5`）を端数畳み込みした結果、
  `uSelectedPatchOwner` との比較が非整数 owner で不一致する」は、**実際にはコードを読む限り既に
  正しく実装されていた**（`shaders.ts` の `nearestPatchOwner` は `int(floor(uPatchData[i].y + 0.01))`
  で明示的に floor しており、`renderer.ts` の `selectedOwner = pi`（整数）と一致する）。isolated
  Chrome（port 5185）で実座標クリック検証した結果、**この floor 比較は実際に正しく動作していた**
  ——patch 配列上の位置 `pi` が `PATCH_MAX_POINTS`（256）の点群予算に収まっている限り、コイン・
  平リング・立体リングいずれもクリック選択で正しくハイライトした（実測: 平リング52パッチ中
  `pi=20` のパッチ、立体リング49パッチ中 `pi=12` のパッチ、どちらも選択でオレンジ色に変化）。
  **真因は別にあった**: 平リング・立体リングは1パッチあたりの点数（節数=10前後）がコインの
  副点（4〜9点）よりずっと多く、`詰める` の既定試行数では**すぐに256点の予算を使い切る**
  （実測: 平リング52パッチ=520点、立体リング49パッチ=490点。どちらも256を大きく超過）。
  256点を超えた分の点は GLSL の uniform 配列に**そもそもアップロードされない**ため、そのパッチは
  CPU側のピッキング（`picking.ts`、予算の制約を受けない）では選択できるのに、シェーダ側のハイ
  ライトは点自体が存在しないので絶対に光らない。「挙動としてはできているっぽい」（=選択情報は
  出る）のに「青くならない」という作者の観察は、この二つの経路（CPU ピッキング vs GPU
  uniform 予算）の食い違いを正確に言い当てていた。典型的な「詰める」（52〜111パッチ）では
  ほとんどのクリックが予算超過後のパッチに当たるため、「ほぼ常に光らない」ように見える
- **色そのものについて**: 作者の言葉は「青くなる」だが、選択ハイライト色はこの Study 含む
  全 Study（cloud-sculpt/pack/rings/skin）で一貫して `vec3(1.0, 0.75, 0.2)`（オレンジ/金）—
  AGENTS §5「余白の色は全 Study 共通のスケールにする…一度決めたら変えない」に従い、新しい
  青を発明せず、既存の選択色をそのままビーズ表示にも流用した（作者の「青くなる」は口語的な
  「色が変わってハイライトされる」の意と解釈。もし本当に色相を青にしたい場合は骨子の色改訂が
  必要になるため、その判断は作者に委ねる旨をここに残す）
- **形状ボタンの active 表示の欠落**（実測で発見・修理）: `main.ts` の `onSkinParamChange`
  コールバックは `patchShape` の変更を記録するだけで、`ui.ts` の形状ボタン（コイン/平リング/
  立体リング）の `mode-active` クラスを更新していなかった（`renderShapeButtons` は初期描画時と
  `syncSkinParams`（履歴の全体差し替え時のみ）からしか呼ばれていなかった）。実機検証で
  「平リング」ボタンをクリックしても選択状態は `getSkinParams().patchShape` では正しく
  `"flatRing"` に変わっているのに、ボタンの見た目は「コイン」のままアクティブ表示され続ける
  ことを確認した。修理: `ui.ts` に軽量な `setPatchShape(shape)` を追加し、`main.ts` の
  `onSkinParamChange` で `key === "patchShape"` のときだけ呼ぶ（他のパラメータのたびに全スライダー
  を再描画する重い `syncSkinParams` は使わない）
- **ビーズ近似表示**（新規、`renderer.ts` の `updateBeads`/`updateBeadSelection`）:
  `THREE.InstancedMesh` の球で、ホスト球（半透明・薄色の下敷き、opacity 0.16）と全パッチの
  全点（近似なし・GLSL uniform 予算の制約を一切受けない）を描く。マテリアルは通常の three.js
  シーンオブジェクトなので、OrbitControls によるオービット/ズームがそのままインタラクティブに
  効く（レイマーチのようにフレームごとにシェーダで再合成する必要がない）。選択パッチの

## Hypothesis

- **完了条件2の地と図の反転は、同じ乱数・同じ履歴から、モード一操作だけで確かに往復できた**
  — `setMode` は場を作り直さず表示と書き出しの式だけを切り替えるので、パッキングを
  やり直す必要が原理的にない設計が実測でも裏付けられた
- **目地 g は両モードで一貫した意味を持つ計器として機能した** — ただし窓モードでは
  「骨の太さ」、プレートモードでは「部品の分離を保つ余裕」という異なる読み方をする、
  という T10 §3 の指示（「逆に」の一言）は、実装してみると単なる符号の違いではなく
  **失敗の意味が違う**ことがわかった: 窓モードで g が足りないと骨が薄すぎて壊れやすい
  （実際の余白の問題）。プレートモードで g が足りないとパッチが融合して「バラバラの部品」
  という意図そのものが崩れる（見かけ／意図の問題）。同じ数値が二種類の失敗を防いでいる
- **プレート版の連結成分数は、パッチ隣接だけを見る速報値（44）とメッシュ実測（22）が
  一致しなかった** — この乖離は「殻の厚み方向を介した間接融合」というライブ計器が
  モデル化していない経路の存在を教えてくれた。作者への正直な報告としては、
  「N 個の分離した部品」を名乗るなら**メッシュ実測の数字を使うべき**で、ライブ計器は
  パッキング直後の目安に留める、という運用が今回の実装からの教訓
- **窓を開けすぎると殻自体が割れる**（実測: 連結成分数2）ことを確認できたのは、
  この Study が「地」を破壊する側の操作（殻の削り取り）も一級の対象にしているからこそ
  観測できた現象で、Y7表面版が予告していた「形態が虚になる」の極端な形の一端だと考えられる
- **測地距離のユークリッド近似**は、今回検証した程度の曲率（S1 の grow ボールクラスタ、
  凹凸の緩やかな卵型）では、パッチが不自然に歪んで見えるほどの誤差は目視で確認できなかった。
  ただし、より鋭い凹みや細い突起を持つホストでは、ユークリッド近似が実際の表面距離を
  大きく過小評価しうる（最短経路が表面をショートカットして反対側の突起まで「見えて」
  しまう）ことは理論上あり得る — この便では未検証

### P0-2（保存後Float32 STLのwatertight判定）の実装と実測

`cloud-sculpt/meshExport.ts`に`inspectSavedStlTopology(triangles, scaleMmPerUnit)`を追加。
`encodeBinaryStl`が`DataView.setFloat32`で行うのと同じ丸め（`Math.fround(v*scale)`）を

ケースを作り、`inspectWatertight`（旧チェック）は`ok:true`のまま、

### P0-3（ゲート合成）の実装と実測

`evaluatePartitionGate`（`partition.ts`、Workerの中・`buildPartitionMeshes`が返す

### P1-1（Wilson score interval）の実装と実測

`wilsonUpper95(successCount, sampleCount)`を実装（正規近似`p±1.96√(p(1-p)/n)`は
該当0件でmargin=0を返す既知の欠陥があった）。単体テストで、k=0でも
n=20000なら上限が0.1%未満の小さいが厳密に正の値になること（旧実装なら0）、k=nでも
上限が1を超えないこと、サンプル数を増やすと同じ比率でも上限が締まることを確認した。
実CoinSRFでは`sampleCount=20000`・該当0件でも`upper95Ratio≈3.00%`となり、
1%の許容値を超えてゲート不合格の一因になった——これは「20,000点のサンプルでは元形状の
体積のうち約4.4%しか内部に当たらない疎な形状で、1%の許容を統計的に保証するには
サンプル数が足りない」ことを正直に表しており、次段でサンプル数を増やすかtoleranceを
見直す判断材料になる（旧実装なら0%と表示され、この不確実性が隠れていた）。

### `raymarchComposite`のロバスト性修正と実座標クリックの完走

`picking.ts`の`raymarchComposite`（クリック選択の球面トレース）を、単純な`t += d`から
(1) ステップを減衰させ（`STEP_DAMPING=0.75`）反復回数を増やす（160→400）damped sphere
trace、(2) それでも当たらない場合のフォールバックとして固定ステップの粗いスキャン＋
二分探索、の2段構成に変更した。原因の仮説（v0.5で未検証のまま持ち越し）: `compositeSdf`が
使うsmooth-min/smooth-boolean合成はLipschitz-1を保証しないため、密なパッキング
（141 coinsが隣接するblend領域）では単純な球面トレースが真の距離より大きい`d`を返し、
薄いpatchを飛び越える可能性がある——今回のロバスト化はこの仮説を修正するのではなく、
仮説が正しくても正しくなくても収束するよう設計した（減衰ステップは過大評価を許容し、
粗いスキャンはLipschitz性に依存しない）。

実CoinSRF（141 coins、`window.__skin`を一切使わずcanvas上の実座標クリックのみ）で、
シード選択2回（`#425`, `#523`）・A/B候補提案（137/4）が過去2回とも同一結果で再現した。
`document.elementFromPoint`同等のヒットテスト回避リスク（AGENTS.md §3「合成
`element.click()`はヒットテストを迂回する」）は、`computer`ツールの実座標クリック
（`pointerdown`/`pointerup`をDOMイベントとして発火）を使うことで避けている。

### `pointInMesh.ts`のバグ発見と修正（単体テスト作成中に判明）

`buildInsideTester`のバケット構築ループが、三角形のbboxがグリッド外縁に触れる場合
（`floor(max/cell) === gridY`、有効な最大index+1）にクランプ前の生の範囲でループしており、
同一三角形を同一バケットへ複数回pushしていた。`isInside`の偶奇判定はヒットのたびに
crossingsを加算するため、この重複pushが同じ交差を2回・4回と数え、偶数/奇数が反転して
内外判定が誤ることがある——ユニットキューブ（境界に触れる面だらけの最悪ケース）で
実際に再現し、`inside(0.3,0.7,0.5)`が`false`（正しくは`true`）を返すことを確認した。
修正はbbox範囲をループ前にクランプすること。この関数は`partition.ts`の
`verifyMeshPartition`（P0-3ゲートが読むMonte Carlo忠実度測定そのもの）が直接使っており、
ゲートの正しさに関わる実バグだった。実CoinSRFでの再実測では、修正前後で
overlap/gap/inconsistentの値は変化しなかった（同一シード・同一形状ではこの特定の
座標整列が起きなかったため、影響ゼロだった）——ただし他の形状・scaleでは発生しうる
既知の欠陥として、今回修正した。

### 実装した式（field.ts, compositeSdf）

現状のplate modeは`dShell = |hostSdf| - thickness/2`とcoin+flatRingの結合fieldをintersectionしていたため、coinが薄いシェル帯に切られて平板になっていた。新パラメータ`SkinParams.coinBulge`（既定0、UI範囲0〜0.32、step 0.005、UI名「コインのふくらみ」）は、**coin形状のplate modeだけ**に効く追加shell半幅で、`coinBulge > 0`のときcoinだけ`dCoinBand = |hostSdf| - (thickness/2 + coinBulge)`という広い帯とintersectionし、coin自身の丸い点群形状を上限として法線方向へふくらみを戻す。flatRing/ring3d/window modeは無変化。

`coinBulge <= 0`は**旧コードパスをそのまま実行する明示的分岐**にした（coin+flatRingを分離してintersectionしてから合成し直すのではなく、結合fieldに対して一度だけintersectionする従来どおりの経路）。smooth boolean（`opSmoothIntersection`）は分配則を満たさないため、`intersection(shell, union(coin,flatRing))`と`union(intersection(shell,coin), intersection(shell,flatRing))`は数値的に一致する保証がなく、既定値0で古いrecipeの再生結果が変わってはならないという要件を満たすには、単に「追加帯の幅を0にする」だけでは不十分だった。

CPU（field.ts）とGLSL（shaders.ts）の両方に同じ分岐・同じ式を実装した。`uPatchData[i].y`のfractional shape encodingをring3dの1ビット（+0.5のみ）からcoin(+0.00)/flatRing(+0.25)/ring3d(+0.50)の3値へ拡張し、`isCoinPoint`/`isFlatRingPoint`/`isRingPoint`で復元する。新規uniform配列は追加せず、既存のuPatchData/uPatchPosをそのまま使う（`uCoinBulge`スカラーのみ追加）。`rg -n "compositeSdf\("`で全call siteを列挙し、picking.ts（raymarchComposite/estimateCompositeNormal）・meshExport.ts（buildSkinMesh）・partition.ts（buildPartitionMeshes内の6箇所）・renderer.ts（updateのuniform書き込み）・main.tsの全呼び出し箇所へ同じ`coinBulge`を明示的に渡した（暗黙のdefaultへ落ちる経路はない）。
